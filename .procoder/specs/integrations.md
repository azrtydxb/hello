# integrations

Status: approved (open questions answered by the user on 2026-10-25; see "Decisions" at the end)

Source: the user's request for (A) directory sync from Google Workspace, Microsoft Active Directory (LDAP/LDAPS) and Microsoft Entra ID, and (B) app/CRM integrations (HubSpot "and others") so people can dial from those apps through the PBX, with click-to-call, call events with screen-pop, and call logging back into the CRM including recording link and duration. The coordinator's app research then fixed the wave order and two cross-cutting choices (see "Defaults chosen"). This spec depends on the `user-accounts` branch merging first (local users, the `user` role linked to extensions, user email, voicemail-to-email, SMTP settings). It extends `.procoder/specs/ai-external-access.md` (OAuth server, scopes, service accounts, MCP), `.procoder/specs/pbx-features.md` (extensions, ring groups, voicemail) and `.procoder/specs/ha.md` (cluster primitives). It is a design only; no implementation is part of this document.

## What exists today (read from the repo, main 9a54d91)

Everything below shapes the design. Items marked **gap** do not exist and are built here.

- **Auth** (`internal/auth`). Roles `viewer < operator < admin`; the `user-accounts` branch adds `RoleUser` (rank 1, below viewer, `/me` only, `GrantableScopes` read+write). Scopes `read`, `write`, `admin`, `secrets`, `session`; `ParseScopes` rejects unknown scopes, so a new scope needs a code change. Credential kinds: session cookie (`hello_session`, SameSite=Strict), legacy token, personal token (`hello_pat_`), OAuth access token (`hello_at_`), service account (client credentials, 1 h tokens), agent. `auth.Require(minRole, scope)` guards each route; the route table is `internal/api/routes.go` and must match `internal/api/openapi.json` (conformance test).
- **OAuth 2.1 server** (`internal/oauth`). Authorization code with PKCE S256, client ID metadata documents, optional DCR (off), service accounts with client secrets, consent screen (`/oauth/consent`, `frame-ancestors 'none'`), refresh tokens, per-key Valkey throttle `Limiter`. `oauth_clients.kind` is `cimd | dcr | service`. A CIMD fetcher already refuses private addresses at dial time (`internal/oauth/cimd.go`, `errPrivateAddress`).
- **MCP** (`internal/mcp`). Tools are generated from the OpenAPI operations; an operation opts out with `x-hello-mcp: {"exclude": "<reason>"}`; response properties marked `x-hello-secret` are redacted. Every new operation in this spec states its MCP decision.
- **Secrets** (`internal/secret`). `secret.Box` (AEAD, key `HELLO_SECRET_KEY`) with a per-record AAD; used for trunk passwords, phone tokens, device secrets. API responses expose `hasPassword`-style booleans only.
- **Users** (`internal/store/users.go`). `users(id, username, password_hash NOT NULL, role, extension_id)`; `SetUserExtension` enforces one user per extension; `ErrLastAdmin` guards demotion. `CreateSession` is called from `login`; there is no OIDC, SAML, LDAP or SCIM anywhere in the code (**gap**; verified by search).
- **Extensions/devices/voicemail** (`internal/store/config.go`, `pbx.go`). `CreateExtension(number, name, externalNumber, check)`, `CreateDevice` (SIP secret generated, HA1 stored, secret sealed), `voicemail_boxes.email`, `extensions.dnd`, ring groups with members. `extensions.number` must match `^[0-9]{2,10}$`. Every config change takes the `hellocfg` advisory lock and runs the whole-config `Check`.
- **Cluster primitives.** `cluster.Store` (Valkey membership, `AcquireRollout` one-per-kind token), and the AI scheduler's PostgreSQL session advisory lock `TryAILock(key)` (`pg_try_advisory_lock(hashtext(key))` on a dedicated connection, released with the connection). The advisory lock is the primitive reused here (generalised, see I-40).
- **Control to SIP requests.** `hello-control` cannot place calls; `hello-sip` alone originates SIP. Two existing patterns: a Valkey list queue with a result key (`livestate/pagetest.go`, polled by `sip/pagetest.go` while the node is READY) and a PostgreSQL queue with `Watch` (`sip/checksync.go`).
- **Call origination in SIP.** `call.originateFor` (`internal/sip/transfer.go`) builds a call to a target and forks legs to an extension's bindings, or runs `s.decide(snap.Routing(), routing.Call{...})` for an external number, then `bridge`/`bridgeAnchored` joins two calls. Paging (`sip/page.go`) shows the per-vendor auto-answer headers (`autoAnswerHeaders`). This is the base for click-to-call.
- **Call state.** `livestate` keeps live calls (`PutCall`, state ringing|connected) and presence (idle|ringing|on-call|dnd). The CDR is written by an in-memory queue (`internal/cdr`) after the call ends. Recordings are a separate row (`recordings`, MinIO object) inserted after the audio is stored, so a recording is not known when the call ends. There is **no call-event bus, no webhook code and no outbound event stream** (**gap**). The only SSE code is the AI chat stream (`api/ai_stream.go`, 15 s keepalive, dedicated nginx location).
- **Web** (`web/`, React). `nav.ts` groups; the Platform group holds Cluster, Diagnostics, System, AI access, Users. `web/nginx/default.conf.template` has per-path locations (AI stream, `/mcp`, `/oauth/`).
- **Recording audio** is served only to authenticated callers (`GET /recordings/{id}/audio`); no signed or expiring link exists (**gap**).

## Problem

An office that already has people in Google Workspace, Active Directory or Entra ID has to create each Hello user, e-mail address and extension by hand and keep them in step when staff join, move or leave. And nobody can dial from the CRM they work in. A salesperson clicks a phone number in HubSpot and nothing happens on their desk phone; a customer rings and the salesperson sees an unknown number; the call is never logged, so the CRM has no record of it, its duration or its recording.

## Users

- **Administrators** connect a directory and see what a sync would change before it runs, pick which attribute is the extension, approve or reject conflicts, and connect a CRM once for the company.
- **Employees** sign in with their company account, click a number in their browser or CRM and have their own desk phone ring first, see who is calling in the CRM, and find the call logged afterwards.
- **Integrators** (Zapier, n8n, scripts) need scoped credentials, signed webhooks they can verify, a REST call-origination endpoint and a live event stream.
- **Security owners** need synced accounts disabled (never silently deleted) when someone leaves, secrets that can never be read back, and no way for an integration to dial arbitrary numbers or reach internal hosts.
- **Operators** need metrics, an audit trail and clear failure states for every connector.

## Defaults chosen for open points

Changing one is a spec edit.

1. **Wave order** follows the coordinator's research: Wave 1 is the generic layer plus HubSpot, directory sync, SCIM and SSO; Wave 2 is Salesforce, Pipedrive, Zoho, Zendesk/Freshdesk, Slack/n8n/Make and contacts/calendar; Wave 3 is Dynamics 365, PSA tools, Clio, Odoo, Bitrix24, the Teams Direct Routing pairing guide and marketplace listings.
2. **Per-customer private apps, no Hello-hosted relay, no marketplace listings (decision 1).** Every OAuth app, Entra app registration, Google client or service account, HubSpot app and Pipedrive app is created by the customer in their own tenant. Hello stores only that customer's client id, secret and tokens, so Hello needs no publisher verification, marketplace review or central secret store. A hosted relay and marketplace listings are not planned (out of scope).
3. **Google access** prefers (a) a per-customer service account that holds a custom read-only admin role in the Admin console (no impersonation), or (b) a per-customer OAuth client with an admin's consent and a stored refresh token, both with read-only directory scopes. Domain-wide delegation (a service account impersonating an admin via `subject`) is supported as a documented fallback, off by default and labelled discouraged in the UI. Whether (a) works for the Directory API on every edition is **verify** in a lab tenant before P9 closes; if it does not, (b) becomes the preferred mode and DWD stays the fallback.
4. **Entra** uses a per-customer app registration with the application permission `User.Read.All` (plus `GroupMember.Read.All` when group mapping is on) and admin consent, client secret or certificate. Hello's own multi-tenant app is never required.
5. **The directory is authoritative for the fields it owns.** A synced field is read-only in the UI and API (`409 managed_by_directory`). Sync never deletes: it disables.
6. **Ring first.** Click-to-call always rings the user's own phone first, then dials the target after the user answers. No auto-answer unless an administrator enables it and the user opts in.
7. **Events are at-least-once, webhooks are signed, and the event id is the dedupe key.** Delivery is never exactly-once.
8. **Recording links** are opaque, unguessable, revocable, expiring tokens in a public path. Recordings go to a CRM only when the connector is switched on for it (decision 2). Default TTL 30 days, refreshed for CRM records (I-33).
9. **Emergency numbers are refused** by the originate endpoint (`422 emergency_not_allowed`): click-to-call carries no location and the user may not be at the phone.
10. **Transport**: SSE, not WebSocket, for the event stream (one-way, resumable with `Last-Event-ID`, proven in this codebase, works through the existing nginx).
11. **New Go dependencies** (each needs the usual review): `github.com/go-ldap/ldap/v3` (LDAP client), `github.com/coreos/go-oidc/v3` with `golang.org/x/oauth2` (OIDC login and JWKS), `google.golang.org/api/admin/directory/v1` or plain HTTPS (decided in P9; plain HTTPS plus `golang.org/x/oauth2/google` is preferred to avoid the large generated client). Graph, HubSpot and the other CRMs use plain `net/http` through the SSRF-safe client (I-41). Nothing here calls an LLM, so go-ai-sdk is untouched.

## In scope

### A. Directory connectors (common engine, `internal/directory`)

- [I-1] **Connector record.** A connector has a kind (`ldap`, `google`, `entra`, `scim`), a name, enabled, a schedule, mode, mappings, a sealed credential and a status. A deployment may have several connectors (for example one AD forest and one Entra tenant); each synced user belongs to exactly one connector (`users.source_connector_id`), and a user found by two connectors is a conflict (I-9).
- [I-2] **Source user model.** Every connector yields the same record: `externalId` (stable: AD `objectGUID`, Entra `id`, Google `id`, SCIM `id`), `username`, `email`, `displayName`, `active`, `extensionRaw`, `groups[]`, plus the raw attribute bag used by mappings. Usernames and emails are compared case-insensitively; `externalId` is the link, never the email.
- [I-3] **Attribute mapping**, configurable per connector, evaluated by one engine for all kinds:
  - `extension`: one source attribute (or an ordered fallback list), then optional transforms: strip non-digits, take the last N digits, regex with one capture group. The result must match `^[0-9]{2,10}$` or the user is flagged `extension_invalid` (not an error for the whole run).
  - `email`, `displayName`, `username`, `active` likewise.
  - Suggested defaults per kind: AD `ipPhone` then `telephoneNumber` for extension, `mail`, `displayName`, `userPrincipalName`, `userAccountControl` bit 2 for disabled; Entra `onPremisesExtensionAttributes.extensionAttributeN` or `businessPhones[0]` (the `ipPhone` property is not in Graph v1.0 **verify**), `mail`, `displayName`, `accountEnabled`; Google `phones[type=work].value`, a custom schema field (`customSchemas.<schema>.<field>`), `primaryEmail`, `name.fullName`, `suspended`; SCIM `urn:hello:params:scim:schemas:extension:pbx:2.0:User:extension`, `phoneNumbers[type eq "work"]`, `emails[primary eq true]`, `displayName`, `active`.
  - The mapping editor shows, for a sample of 20 real users from the source, the raw value and the mapped result before saving (same data as the dry-run, I-8).
- [I-4] **Group mapping.** Rules `(source group) -> Hello role` (`user`, `viewer`, `operator`, `admin`; highest matching wins; default `user`) and `(source group) -> ring group` (add the user's extension as a member). Matching is on the group's stable id with the name shown for readability. Admin from a directory group is off unless the connector sets `allowAdminFromDirectory` (privilege escalation guard, T-8). Ring-group rows created by sync carry `source_connector_id`; sync removes only its own rows and never touches manual members.
- [I-5] **Ownership and source of truth.** Per connector a mode: `authoritative` (default; directory overwrites mapped fields on every run), `create_only` (directory seeds a field once, then Hello owns it) or `link_only` (never create users; link existing local users by email, then manage them). The set of mapped fields is the set of read-only fields: the API returns `managedBy: {connector, fields[]}` on a user, the UI shows a lock and the connector name, and a write to a managed field gets `409 managed_by_directory`. Unmapped fields (role when no group rule exists, for example) stay editable.
- [I-6] **Adopting existing local users.** A local user (no connector) is adopted only when the preview lists it under `adopt` and an administrator confirms; matching key is the verified email, then username. Local admins are never adopted, demoted or disabled by sync, whatever the directory says (T-8).
- [I-7] **Deprovisioning disables, never deletes.** A linked user that is absent from, or inactive in, the source for 2 consecutive complete runs (configurable 1 to 10; immediate for `active=false`, SCIM DELETE or `accountEnabled=false`) is disabled: `users.disabled_at` set, sessions deleted, personal tokens and OAuth grants revoked, SSO refused, and optionally (`disableDevices`, default on) the user's devices disabled. The extension, voicemail box and its messages and CDRs are kept. A user that reappears is re-enabled. Hard deletion is a separate manual administrator action. **Mass-deprovision guard:** if a run would disable more than 20 percent of linked users (minimum 5), it halts as `needs_confirmation` and applies nothing; this protects against an empty filter, a wrong base DN or a partial API outage.
- [I-8] **Dry-run preview with a diff.** `POST .../sync` with `dryRun=true` runs the whole pipeline, writes a `directory_sync_runs` row with status `preview` and one `directory_sync_changes` row per change (`create`, `update` with field-level before/after, `link`, `adopt`, `disable`, `enable`, `conflict`, `skip`, `error`), and changes nothing else. `POST .../runs/{id}/apply` applies that preview; if it is older than 15 minutes or the source changed (diff hash differs on re-read) it answers `409 stale_preview` with a fresh preview. The UI shows counts, a filterable table, and per-row reasons; conflicts need a decision (skip this run, or override) that is audited.
- [I-9] **Conflict rules**, each a distinct reportable reason: extension number already linked to another user; extension number belongs to an extension that is a different kind of record (door, trunk-internal number once those land); two source users map to one extension; email already used by another user; username collision with a local user; the user is claimed by another connector; extension value invalid. A conflicted user is left unchanged, the rest of the run proceeds.
- [I-10] **Linking to extensions.** With `user-accounts`, a user may link to more than one extension; sync manages exactly one (the mapped one) and leaves manually added links alone, recording which link it owns (`user_extension_links.source_connector_id`). If the mapped extension does not exist: with auto-create off, a `conflict: extension_missing` row; with auto-create on, I-11.
- [I-11] **Optional auto-provisioning** (per connector, default off): when a user has no extension value, or the value names no extension, allocate the next free number in a configured range (for example 2000-2999; free = no extension, no feature code, no reserved prefix, checked by the existing whole-config `Check`), create the extension named from the display name, one SIP device (secret generated by the existing device code, shown nowhere; an administrator rotates it from the device page when provisioning a phone), and a voicemail box with the user's email (voicemail-to-email from `user-accounts`). Allocation is serialised under the `hellocfg` lock so two runs and manual edits cannot collide. A user's allocated number is stable: re-runs never renumber. Written back to the directory? No: Hello never writes to a directory (read-only scopes everywhere).
- [I-12] **Schedule and manual run.** Interval per connector (default 60 min, minimum 5, `0` = manual only) plus "Run now" and "Preview now". Incremental where the source supports it (Entra `users/delta`, AD `whenChanged>=` / USN) with a forced full run every 24 h (needed to detect absences). Runs have a timeout (default 15 min) and a user cap (default 20,000) after which the run fails visibly rather than silently truncating.
- [I-13] **HA: one node syncs.** Every `hello-control` replica ticks the scheduler; a replica runs a connector only after taking `pg_try_advisory_lock(hashtext('hello:dirsync:<connector id>'))` on a dedicated connection, so a dead replica's lock disappears with its connection and another takes over on the next tick. "Run now" inserts a `queued` run row that whichever replica holds (or can take) the lock picks up. A run row left `running` by a dead replica is closed as `failed: replica_lost`. SCIM (push) needs no lock; each request is a transaction and uses row locks.
- [I-14] **Secrets.** Connector credentials (LDAP bind password, Google service-account JSON or OAuth client secret and refresh token, Entra client secret or certificate private key, SCIM bearer token hash) are written through `secret.Box.Seal` with AAD `directory:<connector id>:<field>`, columns `*_enc`. They are write-only: `GET` returns `hasSecret`/`hasBindPassword`-style booleans and the non-secret metadata (client id, tenant id, bind DN, certificate fingerprint), never a value. Changing a connector's host, bind DN or tenant requires re-entering the secret (prevents redirecting a stored secret to an attacker's host, T-4). Secrets never appear in logs, audit rows, error text, `directory_sync_changes`, MCP output or metrics labels; connector errors are classified and scrubbed (`auth_failed`, `tls_untrusted`, `unreachable`, `timeout`, `quota`, `bad_filter`) with a short detail that never echoes a credential or full response body.

#### A1. Active Directory / LDAP

- [I-15] **Config**: `url` (`ldaps://host:636` or `ldap://host:389` with StartTLS), `bindDn`, bind password (sealed), `baseDn`, `scope` (default subtree), `userFilter` (default `(&(objectCategory=person)(objectClass=user))`), `groupBaseDn` and `groupFilter` when group mapping is on, `caCertPem` (public certificate bundle, not a secret), `serverName` for verification, `pageSize` (default 500), `timeoutSeconds`, and `ldapBindLogin` (I-30).
- [I-16] **Transport.** Plain `ldap://` without StartTLS is refused (`400 tls_required`); certificate verification is always on (no insecure-skip option; a private CA is supplied through `caCertPem`; a lab-only environment switch `HELLO_DIRECTORY_ALLOW_PLAINTEXT_LDAP` exists, off by default, and logs a warning on every use). Referrals are not followed. TLS 1.2 minimum.
- [I-17] **Paging and limits.** Simple Paged Results (RFC 2696) with `pageSize` (AD's default MaxPageSize is 1000; 500 is safe), a size cap per run and a per-page timeout. Disabled accounts are fetched (the filter does not exclude them) and decided from `userAccountControl` bit 2; `objectGUID` is converted from binary to its canonical string; nested group membership uses `LDAP_MATCHING_RULE_IN_CHAIN` (1.2.840.113556.1.4.1941) only when `nestedGroups` is on (documented as slow on large forests).
- [I-18] **Injection safety.** The administrator's `userFilter` is parsed on save (`ldap.CompileFilter`) and rejected if malformed; every value Hello interpolates into a filter or DN (a username at LDAP login, a group DN lookup) goes through `ldap.EscapeFilter`/`ldap.EscapeDN` and a length and NUL check; a bind with an empty password is refused before any network call (an empty-password simple bind is an anonymous bind and "succeeds" on many servers).
- [I-19] **Test connection** (`POST .../test`): connect, StartTLS/LDAPS verify, bind, one base search with a size limit of 20; the result lists the server certificate subject and expiry, the number of matched users in the first page and the sample used by the mapping editor. It writes an audit row and no data.

#### A2. Google Workspace

- [I-20] **API**: Admin SDK Directory API `users.list` (`customer=my_customer`, `projection=full` or `custom` with `customFieldMask`, `viewType=admin_view`, `maxResults=500`, page tokens) and `groups.list`/`members.list` when group mapping is on. Scopes (read-only only, enforced in code by an allow-list): `admin.directory.user.readonly`, `admin.directory.group.readonly`, `admin.directory.group.member.readonly`. There is no change-since filter on `users.list`, so every Google run is a full list (fine up to the user cap). Suspended users and users whose `archived` is set are `active=false`.
- [I-21] **Auth modes** (default 3): `service_account` with no `subject` (the service account holds a custom read-only admin role), `oauth_admin` (customer-created OAuth client, admin consent once, refresh token sealed; offline access), and `service_account` with a `subject` (domain-wide delegation, discouraged, off by default, requires typing the admin email and the exact scope list is shown for the customer to authorise). Hello requests no write scope in any mode.

#### A3. Microsoft Entra ID

- [I-22] **API**: Microsoft Graph v1.0 `GET /users` with `$select`, `$top=999` and `@odata.nextLink` paging; `GET /users/delta` for incremental runs (delta tokens stored on the run row; an expired token forces a full run); `GET /groups/{id}/members` for group rules. Auth: OAuth 2.0 client credentials against `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`, scope `https://graph.microsoft.com/.default`, application permissions `User.Read.All` (+ `GroupMember.Read.All`). Client secret or certificate (a signed client assertion; private key sealed). Graph 429 and `Retry-After` are honoured with a per-run budget.

#### A4. SCIM 2.0 server (push from Okta, Entra provisioning, JumpCloud)

- [I-23] **Endpoints** under `/scim/v2` (a separate listener path, not `/api/v1`): `GET/POST /Users`, `GET/PUT/PATCH/DELETE /Users/{id}`, `GET/POST /Groups`, `GET/PATCH/DELETE /Groups/{id}`, `GET /ServiceProviderConfig`, `/Schemas`, `/ResourceTypes`, per RFC 7643/7644. `Bulk` is advertised unsupported. Filtering supports `userName eq`, `externalId eq`, `emails.value eq`, `and`; `startIndex`/`count` paging capped at 200. PATCH implements RFC 7644 section 3.5.2 add/replace/remove, including the no-`path` form and the string-boolean forms (`"True"`/`"False"`) that Entra sends **verify** against each IdP's current behaviour in the lab. Content type `application/scim+json`.
- [I-24] **Auth**: a SCIM connector issues one bearer token (`hello_scim_` prefix, shown once, only its SHA-256 stored) that is valid for `/scim/v2` only and carries no API scope. The token's owner connector decides ownership (I-5). SCIM `DELETE` and `active:false` both disable (I-7); SCIM never creates `operator` or `admin` unless `allowAdminFromDirectory` and a group rule say so. Mappings (I-3) apply to the SCIM payload, including the custom extension schema `urn:hello:params:scim:schemas:extension:pbx:2.0:User` with `extension`.
- [I-25] **No dry-run for push.** The mass-deprovision guard counts SCIM disables per rolling hour against the same 20 percent rule and, once exceeded, answers `429` with a SCIM error and pauses the connector until confirmed in the UI. Per-token rate limit 600 requests per minute.

### B. SSO (OIDC login)

Nothing exists today (searched for OIDC, SAML, LDAP: none). New:

- [I-26] **Providers**: `google` and `entra`, each configured by the customer's own client id and secret (sealed), plus for Entra the tenant id. Issuer pinned: `https://accounts.google.com`, `https://login.microsoftonline.com/<tenant>/v2.0`; `common`/`organizations` tenants are refused. Authorization code + PKCE S256, `state` and `nonce` mandatory, discovery and JWKS cached and refreshed on `kid` miss, `iss`, `aud`, `exp`, `nonce` validated, `azp` checked when present.
- [I-27] **Routes**: `GET /api/v1/auth/oidc/{provider}/start` and `GET /api/v1/auth/oidc/{provider}/callback` (both public). The callback is a cross-site top-level redirect, so the existing `SameSite=Strict` session cookie cannot be used to carry state: `state`, `nonce` and the PKCE verifier are stored server-side in Valkey (10 min TTL, single use) and bound to the browser by a short-lived `hello_oidc` cookie with `SameSite=Lax`. After validation the same session creation code as `login` runs (extracted to a shared helper) and `hello_session` (Strict) is set on the redirect response.
- [I-28] **Mapping to users.** Order: (1) an existing link `(provider, subject)` in `user_identities`; (2) for the first login only, a directory-synced user whose mapped email equals the verified ID-token email, and whose tenant matches: Google `hd` equals a configured domain and `email_verified` is true, Entra `tid` equals the configured tenant and `oid` equals the synced `externalId`. Local (non-synced) users, and in particular local admins, are never matched by email (account takeover guard, T-7). A disabled user is refused with a generic message. No just-in-time creation unless the connector has `jit` on (default off; synced users already exist). Because synced users have no local password (I-29), this is their only way in.
- [I-29] **SSO is required for synced users (decision 3).** A user created or linked by a directory connector or SCIM has no local password and cannot get one: `users.password_hash` is a reserved non-matching marker (or NULL, decided with `user-accounts`), password login for such a user always fails with the generic message, and every route that sets a password (admin set-password, self-service change, `must_change_password` flow, `hello-control user` CLI) refuses a synced user with `409 managed_by_directory`. A synced user signs in only through the IdP: OIDC for Google and Entra connectors, LDAP bind for AD connectors that have no OIDC provider (I-30). A SCIM-created user signs in through the OIDC provider configured for its tenant. There is no fallback to a local password in any failure (IdP down, token expired, connector disabled): the user waits for the IdP or an administrator acts.
  - **Guard against lock-out at configuration time.** A connector cannot be enabled, and a preview cannot be applied for `create`/`adopt`, unless a login method exists for its users (`400 no_login_method`: an enabled OIDC provider whose domain/tenant matches, or `ldapBindLogin` on). Adopting a local user into a connector removes its password hash only after the preview is confirmed, and an adopted user keeps no local login.
  - **Break-glass administrators.** `users.break_glass` marks local administrators (local = no connector, not synced) that keep password login regardless of `ssoRequired`. The system always keeps at least one enabled break-glass admin: creating the first break-glass admin is part of enabling SSO enforcement; removing the flag from, disabling, demoting, deleting or adopting the last enabled break-glass admin is refused by the store in the same transaction as the change (`409 last_break_glass`, alongside the existing `ErrLastAdmin` locking that serialises concurrent changes), and a directory sync or SCIM request that would touch such a user is skipped as a conflict `protected_local_admin`. Break-glass sign-ins are audited with a distinct action and counted in `hello_break_glass_logins_total`.
  - `ssoRequired` (global, default on once any provider exists) hides the password form for everyone except break-glass users; local non-synced users who are not break-glass may still be allowed a password by an administrator toggle `localPasswordsAllowed` (default on, so existing sites are not locked out; off forces SSO for all but break-glass).
- [I-30] **LDAP bind login** is the sign-in method for synced users of an AD connector that has no OIDC provider (per-connector `loginMethod`: `oidc` or `ldap_bind`; one is mandatory, I-29). The password is verified by an LDAPS/StartTLS bind as the user (DN looked up with the escaped filter, I-18); Hello never stores or logs it, and the bind uses the user's own credentials, not the service bind account. Throttle: 5 failures per user and per IP per 10 minutes (Valkey `Limiter`), a constant-time-ish failure path like `SpendPasswordCheck`, and a disabled or absent user is refused before any bind. Account lockout state in AD is respected (a locked-out AD account fails to bind and stays failed).

### C. Integration platform

- [I-31] **Scopes for third parties.** Three new orthogonal scopes, added to `AllScopes`, `ParseScopes` and the OpenAPI scope enum: `calls` (originate and hang up one's own call, read the state of calls one started), `events` (read the event stream and event history), `recordings` (mint and read recording links). `GrantableScopes`: `user` gets `calls`, `events`, `recordings` limited to their own extensions by a handler-level ownership check (not by the scope); `viewer` gets `events`; `operator` all three; `admin` all. Admin-only credentials for webhooks stay under `admin`. Credentials are the existing ones: personal tokens (`hello_pat_`), service accounts, and OAuth access tokens. For third-party apps run by a person (the HubSpot iframe, the browser extension, a Salesforce softphone) the credential is an OAuth access token from the authorization-code flow, so the token acts as that user.
- [I-32] **Pre-registered first-party clients.** `oauth_clients.kind` gains `preregistered` for Hello's own apps (`hello-dialer`, `hello-extension`, `hello-hubspot`, `hello-salesforce`). They are public clients with PKCE, fixed redirect URIs derived from the deployment (`https://<ext-id>.chromiumapp.org/` for the browser extension; the iframe pages' own `/integrations/<app>/callback`), marked Verified so the consent screen names them. Consent for these opens in a popup window (the consent page forbids framing and third-party iframes may not receive Hello's cookies), and the app receives the token by `postMessage` to its own origin.
- [I-33] **Service-account restrictions.** A service account may carry `extensionScope` (list of extension numbers it may originate for or receive events about; null = all, set by an administrator). A user-bound token is always restricted to the user's linked extensions.
- [I-34] **Call events.** `hello-sip` emits these event types (the registry is the single source for webhooks, the stream and the UI):
  - `call.ringing` (one per ringing extension: a ring group yields one per member; `extension` names the subject), `call.answered`, `call.ended`, `call.missed` (inbound or internal call that reached an extension and ended with no answer by anyone in that extension's path: reason `no_answer | busy | dnd | cancelled | unreachable`; a call picked up elsewhere in a ring group is not missed for the others), `call.originate.progress` (state changes of a click-to-call, I-37), `call.recording.ready` (recording row inserted, carries `recordingId`, `durationMs`), `call.completed` (CDR persisted, carries `cdrId`).
  - Common payload (`apiVersion` in the envelope; additive changes only): `id` (unique event id), `type`, `createdAt`, `data{callId (the CDR correlation id), direction, extension, userId, from{number,name,extension}, to{number,name,extension}, trunk, startedAt, answeredAt, endedAt, durationMs, billableMs, disposition, reason, originateId, cdrId, recordingId}`. Recording audio, SIP bodies and DTMF are never in events.
  - Because a recording is stored after the call ends, a CRM log is created at `call.completed` and gets its recording link when `call.recording.ready` arrives (I-53).
- [I-35] **Event pipeline.** `hello-sip` appends events to a Valkey stream `hello:events` (`XADD ... MAXLEN ~ 10000`) from a bounded in-memory queue (1,000, drop-newest with `hello_events_dropped_total`; the SIP path never waits on Valkey or PostgreSQL, like the CDR queue). `hello-control` runs a consumer group `ingest` that, in one transaction, inserts `integration_events` (deduplicated on the event id) and one `webhook_deliveries` row per matching endpoint, then `XACK`s; unacknowledged entries are reclaimed by another replica (`XAUTOCLAIM`) so a crashed consumer loses nothing. `integration_events` keeps 7 days (configurable 1 to 30).
- [I-36] **Event stream (SSE).** `GET /api/v1/events/stream?types=&extension=` with `Accept: text/event-stream`, `id:` per event, a 15 s keepalive comment, `Last-Event-ID` resume from `integration_events` (up to its retention), write deadline cleared (same technique as `ai_stream.go`), and a dedicated nginx location with buffering off. Scope `events`; a `user`-role or user-bound credential receives only events whose `extension` it owns; a service account receives what its `extensionScope` allows. Browsers' `EventSource` cannot send an `Authorization` header, so `POST /api/v1/events/tickets` mints a single-use 30-second ticket usable as `?ticket=`; fetch-based clients (the extension, the iframes) use the bearer header. Limits: 5 concurrent streams per credential, 200 per control pod; one blocking Valkey read per pod fans out in memory. The control process fans the stream out only to clients on that pod.
- [I-37] **Click-to-call: `POST /api/v1/calls/originate`.**
  - Request: `{destination, extension?, deviceId?, callerId?, autoAnswer?, idempotencyKey (or Idempotency-Key header)}`. Response `202 {originateId, state}`. `GET /api/v1/calls/originate/{id}` returns state; `DELETE` cancels while ringing; states `queued | ringing_agent | agent_answered | dialing_target | connected | ended | failed(reason)` with reasons `no_registration | agent_no_answer | agent_busy | agent_dnd | target_busy | target_no_answer | route_denied | rate_limited | node_unavailable`.
  - Who: `extension` defaults to the caller's single linked extension; a `user` credential may name only its own; an operator/admin or a service account within its `extensionScope` may name any (audited, with the acting client). `deviceId` picks one of the extension's devices; otherwise all registered contacts ring.
  - Flow: `hello-control` validates, applies the limits (I-39), inserts an `originate_requests` row and enqueues it on a Valkey list `hello:originate:queue` (same shape as `hello:pagetest:queue`, with an `ID` for idempotency); any READY `hello-sip` node takes it (polling at 250 ms or woken by a pub/sub notification so dispatch is under one second) and creates a call. **Leg A** is an INVITE to the extension's bindings, built like the extension branch of `originateFor`, with caller name "Call to <target name or number>" so the user knows why the phone rings, and a ring tag if the ring-tag feature has landed. If `autoAnswer` is true and allowed (I-39) the vendor auto-answer headers from `page.go` are added. On answer of leg A (not on 180), **leg B** is routed with `s.decide(...)` as if the extension had dialled the destination (internal extension, ring group, or outbound route with all existing class and permission checks and rewrites), and A and B are bridged by the existing `bridge`/`bridgeAnchored`. If A is not answered within `originateRingSeconds` (default 30) the request fails with `agent_no_answer` and B is never dialled.
  - CDR: one CDR covers the bridged call, `source` the extension, with new columns `origin` (`phone | api`) and `origin_client` (OAuth client or token id), so reports separate click-to-call from direct dialling.
  - Caller-ID rules (in order): the outbound route's decision for the extension decides the presented number; a `callerId` in the request is honoured only if it is one of the numbers permitted for that extension by the routing configuration (never arbitrary; `422 caller_id_not_allowed`); anonymous is never settable by the API. The called party sees the same number it would see if the user had dialled from the desk phone.
  - Refusals: emergency numbers (`422 emergency_not_allowed`), destinations the route table denies (`route_denied`), more than 64 digits, anything that is not a dialable string (digits, `+`, `*`, `#`; no SIP URIs, so a caller cannot make Hello dial `sip:...` hosts).
  - HA: if the node that owns the call dies the call follows the existing in-call handoff for anchored calls; the request itself is at-least-once on the queue and idempotent on `idempotencyKey` (Valkey, 10 minutes).
  - MCP: excluded (`x-hello-mcp: {"exclude": "places phone calls"}`), so an AI agent cannot dial.
- [I-38] **Click-to-dial from browsers.**
  - A small page at `/dial?n=<number>` in the web UI (works for any role including `user`): shows the number and the extension that will ring, requires one click to confirm (stops a malicious page triggering calls through a link), calls originate, shows live state from the event stream, and offers hang-up.
  - The console registers itself as the `tel:` handler with `navigator.registerProtocolHandler("tel", ".../dial?n=%s")` after an explicit "Use Hello for phone links" button (`tel` is on the HTML safelist; `callto` is not, so `callto:` is handled only by the browser extension, I-55; support varies by browser, **verify** per browser).
  - A Chrome/Edge (Manifest V3) browser extension is its own phase (P5).
- [I-39] **Abuse limits for originate** (toll-fraud and harassment controls): per credential 10 per minute and 200 per day, per extension 1 call in setup at a time and 30 per hour, per destination 3 per 10 minutes, global per deployment 600 per hour; an administrator setting "click-to-call allowed destinations" (inherit routing, or restrict to internal plus a country allow-list) and "auto-answer allowed" (off). Exceeding sends `429` with `Retry-After`, increments `hello_integration_rate_limited_total` and, over a threshold, raises an audit row `originate.anomaly`. An hourly alert is exposed as a metric for existing alerting.
- [I-40] **Generalised lock.** The AI-named `TryAILock` in `store` becomes `TryLock(key)` (the AI call sites keep their keys); the directory scheduler, the webhook dispatcher leader tasks (purge, retry sweeper) and the CRM refresher use it. No behavioural change for AI.
- [I-41] **SSRF-safe outbound HTTP** (`internal/safehttp`): one client used by webhooks, CRM connectors, Graph/Google, OIDC discovery and recording-link fetches, extracted from the dial-time check in `oauth/cimd.go`. It validates the resolved IP at connect time (so DNS rebinding cannot swap it), refuses loopback, link-local (including 169.254.169.254), unspecified, multicast, `100.64.0.0/10`, IPv4-mapped IPv6 and IPv6 ULA unless the caller passes an explicit allow-list, never follows redirects across hosts (webhooks: no redirects at all), caps response bodies (64 KiB for webhooks, 8 MiB for API calls), sets timeouts (10 s default), and disables proxies from the environment. Exceptions: LDAP targets and `allowPrivate` webhooks are private by nature; these use an administrator-set CIDR allow-list (`HELLO_INTEGRATIONS_ALLOWED_CIDRS`, default RFC 1918 ranges only; link-local, loopback and metadata ranges are never allowed).
- [I-42] **Outbound webhooks.**
  - Endpoint: name, `https` URL (http only for `allowPrivate` endpoints in the allow-list), event type filter (exact types or `call.*`), optional extension filter, enabled, secret (sealed, shown once at creation and on rotation).
  - Request: `POST` JSON, `Content-Type: application/json`, headers `Hello-Event-Id`, `Hello-Event-Type`, `Hello-Delivery` (unique per attempt), `Hello-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256(secret, t + "." + rawBody)>`; during the 24-hour rotation window both secrets sign (`v1=` repeated). Receivers must reject timestamps older than 5 minutes and dedupe on `Hello-Event-Id`. Comparison guidance uses constant-time compare.
  - Delivery: 2xx is success. Retry on network errors, 5xx, 408 and 429 (honouring `Retry-After` up to 1 hour) with delays 10 s, 30 s, 2 min, 10 min, 1 h, 4 h, 12 h (jittered, 7 attempts, about 17 hours). Any other 4xx goes straight to the dead-letter state; 410 additionally disables the endpoint. After exhausting retries a delivery is `dead` (the dead-letter queue is the set of `dead` rows, kept 30 days), listed in the UI with last status and error, redeliverable one at a time or in bulk (a redelivery is a new attempt with the same event id). An endpoint with 50 consecutive failures is auto-disabled (`disabled_reason`), audited, and e-mailed to administrators when SMTP is configured.
  - Concurrency: workers claim `webhook_deliveries` with `FOR UPDATE SKIP LOCKED` on every control replica; 4 in flight per endpoint, 32 per replica. Ordering is best effort per call (`createdAt` and a per-call `sequence` are in the payload) and not guaranteed.
  - `POST .../test` sends a `webhook.test` event synchronously and shows status code, latency and the first 1 KiB of the response.
  - REST-hook compatibility for Zapier: `POST /api/v1/webhooks` is idempotent on `(url, events)` and `DELETE` by id unsubscribes.
- [I-43] **Contact lookup** `GET /api/v1/lookup/number?number=` (scope `read`; `user` role allowed): normalises with the existing dial context (`phonebook.Dialing.Key`), returns the best match from extensions, the company phonebooks and, for that user, personal contacts, with the same ordering as the caller-name lookup; used by connectors and the dialer.
- [I-44] **Call history for integrations.** The existing `GET /api/v1/cdrs` and `/cdrs/{id}` already return call data; this spec adds `origin`, `origin_client` and `recordingId` to the CDR response, and `GET /api/v1/cdrs/{id}/recording-link` (I-45).
- [I-45] **Recording links.** `POST /api/v1/recordings/{id}/links` (scope `recordings`, own extensions for user credentials) returns `{url, expiresAt}`. The URL is `https://<public host>/r/<token>.wav` (the suffix is required by HubSpot, which plays only `.mp3`/`.wav` and accepts only HTTPS). The token is 256 bits of randomness; only its SHA-256 is stored in `recording_links` with the recording id, expiry, optional `maxUses`, the minting credential and the connector. `/r/` is a public path (no session) served by `hello-control`: validates the hash and expiry, streams the audio with `Range` support, `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex`, and rate limits per token and IP (30 per minute). Links are revocable (`DELETE`), revoked automatically when the recording is deleted, and every mint is audited; hits are counted on the row and in `hello_recording_link_hits_total{result}`. Default TTL 30 days (1 hour to 365 days per connector). Minting a link for a call the credential's user was not part of is `403`.
- [I-46] **Contact consent note.** Recording notice and consent stay governed by the existing `HELLO_MEDIA_RECORDING_NOTICE`; connectors that publish recording links show a warning on enabling that recordings leave Hello's storage in the sense that a CRM user with the link can play them.

### D. CRM connectors (framework `internal/crm`)

- [I-47] **Connector interface.** Capabilities flags per connector: `lookup`, `logCalls`, `recordings`, `clickToCall`, `screenPop`, `ticket`. Operations: `Lookup(number)` returning contact id, name, company, url; `LogCall(CallLog)` returning an external reference; `UpdateCallLog(ref, patch)`. Lookups are cached in Valkey 5 minutes (negative 60 s) and bounded to 1.5 s at ringing time (a slow CRM never delays the ring). Logging runs from the event pipeline as a durable job (`crm_call_logs`: unique on `(connector, callId)`, status, external id, attempts, next attempt, last error) with the same retry schedule as webhooks and a dead-letter state visible in the UI. User mapping from Hello user to CRM user is by verified email (never by display name); an unmapped user's calls are logged to the connector's fallback owner or skipped, per setting.
- [I-48] **Auth model per connector** (Default 2: the customer creates the app). `crm_connections` holds `scope = org | user`, sealed tokens (`access_enc`, `refresh_enc`), expiry, granted scopes, external account id, and a status (`connected | needs_reauth | revoked`). A refresh failure marks `needs_reauth`, stops that connection's jobs (not retried forever), shows a banner, and e-mails the owner.
- [I-49] **Screen-pop** is delivered where the user already is, never by Hello popping a window: (a) in the CRM through the connector's own mechanism (HubSpot SDK `incomingCall`, Salesforce Open CTI `screenPop`), (b) in Hello's `/dial` and browser extension via the SSE stream with the lookup result attached. The event is the same `call.ringing` filtered to the user's extension.

## Out of scope

- Hello-hosted relay, marketplace-distributed shared OAuth apps and all marketplace listings (HubSpot, Zoho PhoneBridge, Pipedrive, AppExchange, Chrome Web Store): not planned (decision 1).
- Zendesk Talk Partner Edition, Dynamics 365 Contact Center, and any softphone that needs WebRTC in the CRM (Hello's desk phones are SIP; Hello has no WebRTC gateway today).
- Two-way directory writes. Hello never writes to a directory; all directory credentials are read-only.
- SAML. OIDC covers Google and Entra, the two requested identity providers; AD-only sites use LDAP bind login. SAML is added only if a customer needs another IdP.
- Importing CRM contacts into phone phonebooks (caller-name on phones). Screen-pop and lookup cover the user's request; the phonebooks-ptt caller-name feature stays as it is.
- Teams Direct Routing implementation (documentation only, P22).
- Real hardware testing of vendor-specific tone and phone behaviours is not touched here.

## Constraints

- Control plane work (connectors, sync, webhook delivery, CRM jobs) lives in `hello-control`; SIP and media stay in `hello-sip`. `hello-sip` never calls out to PostgreSQL-backed integration code on the call path; it only appends to the bounded event queue.
- Every new API operation is added to `internal/api/openapi.json` with `x-hello-scope`, `x-hello-role` and an MCP decision, and to the route table, so the conformance test passes. Operations returning or accepting secrets mark properties `x-hello-secret`.
- Every configuration write goes through the store with an audit row and uses the `hellocfg` lock/`Check` where it creates extensions or ring-group members.
- All timestamps UTC; numbers are normalised with the existing dial context.
- Migrations: numbers are "next free at implementation time". Other branches hold 00017 to 00023 and the canvas, multicast channels and user-accounts will take the next few; each phase takes the next free number on rebase and never edits an applied migration.
- Config: `HELLO_PUBLIC_URL` is required for OIDC, `/r/`, `/scim/`, the iframes and the OAuth first-party clients; without it these features answer `404`/are hidden and the rest works, like MCP today.

## Edge cases

- Directory returns an empty list (outage, wrong filter): the mass-deprovision guard stops the run; an empty result for a connector that previously returned users is `failed: empty_result` unless confirmed.
- Same person in AD and Entra (hybrid): both connectors may list them; the first connector to link wins and the second reports `claimed_by_other_connector`. Recommend running only one connector per source of truth.
- Extension number reused (leaver's number to a new hire): the leaver is disabled and their link kept until released; the new hire conflicts until an administrator unlinks the old user (a one-click "release extension" on the conflict row).
- Email changes in the directory: the link is by `externalId`, so the user is updated, not duplicated; a change that collides with another user is a conflict.
- User deleted then recreated in the directory (new GUID): treated as a new user; the old one is disabled by absence; the preview shows both, and an optional "re-link by email" action merges.
- Click-to-call while the user's phone is on another call: leg A gets busy; state `failed: agent_busy` (call waiting is a phone feature and is not forced).
- Click-to-call destination equals the user's own extension: refused (`422`).
- A webhook receiver is slow (30 s): timeout at 10 s counts as a failed attempt; a flood of events never blocks other endpoints (per-endpoint concurrency).
- Valkey outage: SIP keeps working, events drop (counted); SSE and webhooks pause; on recovery the stream resumes from the last acknowledged entry.
- Duplicate engagement in HubSpot (iframe and server both log): prevented by `crm_call_logs` unique key and the engagement-id handshake; if the engagement id arrives late, the server's engagement is the one kept and the iframe's is patched.
- OIDC callback replay or state reuse: single-use Valkey state, rejected.
- An SSE client behind a proxy that buffers: the keepalive and `X-Accel-Buffering: no` header; the UI shows "stream stalled" after 45 s.
- Time skew: webhook timestamp window 5 minutes; receivers get the server `Date` header on the test ping.
- A CRM revokes the app: refresh returns `invalid_grant`, the connection becomes `needs_reauth` once, not on every retry.

## Failure modes

- IdP outage: synced users cannot sign in and there is no local-password fallback (decision 3); existing sessions continue until they expire; break-glass administrators sign in locally and can inspect and, if needed, disable `ssoRequired`.
- LDAP/Google/Entra unreachable: the run fails with a classified code, the previous state stays, `hello_directory_last_success_timestamp` ages and an administrator e-mail goes out after 3 consecutive failures when SMTP is configured; nothing is disabled.
- Partial page failure mid-run: the run aborts without applying (the pipeline reads everything first, then applies in one transaction per batch of 200 users with the run row recording progress; a failed batch rolls back and the run ends `failed`; completed batches stay valid because each is idempotent).
- Replica dies during a run: its advisory lock is released, the run row is closed `failed: replica_lost`, the next tick re-runs.
- `hello-sip` node dies after taking an originate request: the request row stays `queued/ringing_agent` and is closed `failed: node_unavailable` after 60 s by a sweeper; the client may retry with the same idempotency key to get the same id and a clear terminal state.
- Webhook DLQ full growth: dead rows are capped at 100,000 per endpoint (oldest dropped, counted); the endpoint is auto-disabled long before.
- CRM rate limits: `429`/`Retry-After` respected; jobs back off per connection; lookups degrade to "no match" rather than delaying the ring.
- Secret box key mismatch: connectors with unreadable ciphertext show `credential_unreadable` and are skipped (same as trunks today); nothing crashes.

## Acceptance criteria

- **AC-1** A dry-run against a fixture LDAP server (in-process, with paging forced at 2 rows per page) lists create/update/disable/conflict rows and changes nothing; applying the same preview applies exactly those rows; a changed source returns `409 stale_preview`.
- **AC-2** With the mapping `extension <- ipPhone`, a user with `ipPhone="+1 (555) 0123"` and the transform "last 4 digits" maps to extension number `0123` and links to that extension; an invalid value yields one `extension_invalid` row and the other users still sync.
- **AC-3** A synced user's email/extension/display name cannot be changed through `PATCH /users/{id}` (`409 managed_by_directory`) and the UI shows the lock; unmapped fields stay editable.
- **AC-4** A user removed in the directory is disabled after the configured number of runs: sessions gone, tokens/grants revoked, devices disabled, extension and voicemail kept; reappearing re-enables. A run that would disable over 20 percent halts as `needs_confirmation` and changes nothing.
- **AC-5** Two control replicas never run the same connector at once (integration test with two schedulers and a real PostgreSQL); killing the lock holder lets the other run on its next tick.
- **AC-6** No connector `GET`, log line, audit row, error body or MCP output contains a stored secret (a test seeds a canary secret and greps every output); changing the host without re-entering the secret is `400`.
- **AC-7** LDAP: a filter containing `)(uid=*` in a username at bind login is escaped and fails safely; an empty password is refused without a network call; plain `ldap://` without StartTLS is refused.
- **AC-8** Entra and Google connectors page through 2,500 users against fakes of Graph and the Directory API, honour `Retry-After`, and request only the read-only scopes (asserted on the token request).
- **AC-9** SCIM: create, replace, PATCH (with and without `path`, string booleans), filter `userName eq`, delete-disables, `ServiceProviderConfig`; Okta, Entra and JumpCloud provisioning tests are recorded in the lab list.
- **AC-10** OIDC: the state is single-use; a wrong issuer, audience, nonce or expired token is refused; a local admin with the same email as the ID token is not logged in; a synced user is, and gets a session identical to a password login.
- **AC-10b** A synced user has no usable password: password login fails generically, and every set-password route and the CLI answer `409 managed_by_directory`; an IdP outage never produces a local-password fallback; enabling a connector with no login method is `400 no_login_method`.
- **AC-10c** The last enabled break-glass admin cannot be disabled, demoted, deleted, unflagged or adopted, including under two concurrent requests (integration test on real PostgreSQL); a sync or SCIM request touching a break-glass admin is skipped as `protected_local_admin`; with `ssoRequired` on, only break-glass users can use the password form.
- **AC-11** `POST /calls/originate` rings only the caller's own extension for a `user` credential; leg B is not dialled until leg A answers; an unanswered leg A ends `agent_no_answer` and dials nothing; the CDR has `origin=api`; emergency numbers, SIP URIs and a foreign `callerId` are refused; 11 requests in a minute give `429`; the same idempotency key returns the same id.
- **AC-12** The event stream delivers `ringing -> answered -> ended -> completed` in order for a test call, resumes after a disconnect via `Last-Event-ID` without loss or duplicates, and shows a `user` credential only its own extensions' events.
- **AC-13** Webhooks: a valid HMAC verifies with the published algorithm; retries follow the schedule (fake clock); a 5xx then 2xx delivers once; a 400 goes straight to dead; 410 disables; the dead letter can be redelivered; a loopback, link-local or DNS-rebinding target is refused at connect time; two replicas never deliver the same row twice concurrently.
- **AC-14** A recording link works without a session, supports `Range`, expires, is revocable, dies with its recording, and is rate-limited; the stored value is only a hash.
- **AC-15** HubSpot fake server: `call.completed` creates one Calls record with duration, direction, status, owner and association; `call.recording.ready` patches `hs_call_recording_url` with an https `.wav` link; an engagement created by the iframe is patched, not duplicated; a missed call is logged as no-answer.
- **AC-16** The OpenAPI document, route table and MCP tool list agree (conformance test); excluded operations are absent from MCP; secrets are marked `x-hello-secret`.
- **AC-17** Every phase leaves `go vet`, the linters, the web tests and the existing e2e/integration suites green and adds tests for its own behaviour (unit, plus a fake of each external API; real-vendor sandbox runs are listed as lab items, not as CI).

## Phased delivery

Prerequisite: `user-accounts` merged (the `user` role, user email and extension links). Each phase is one or a small number of PRs, independently mergeable, ships its migration (numbered at implementation time), API, OpenAPI entries, UI, tests, metrics, audit and documentation, and leaves nothing half-wired (a feature is either fully usable end to end or not reachable). Each phase opens by re-reading the vendor documentation it depends on and recording the result.

**Wave 1: generic layer, HubSpot, directory, SSO**

- **P0 Foundations.** New scopes `calls`/`events`/`recordings` (auth, OpenAPI enum, `GrantableScopes` for viewer, operator and admin; the `user`-role grant follows `user-accounts`); `TryLock` generalisation (I-40); `internal/safehttp` (I-41), with the client ID metadata fetcher moved onto it; `oauth_clients` kind `preregistered` and `extension_scope` (the first-party clients themselves are registered by the phase that ships each app: P3 dialer, P5 extension, P6 HubSpot, P13 Salesforce); `Actor.ExtensionScope` carried by service-account tokens; Integrations nav group, overview and API access pages (service accounts with the new scopes and extension limit, personal tokens). Migration numbering rule: just before merging, renumber to (highest on origin/main)+1 and update the `test/integration/migrate_*_test.go` counts, because goose rejects a lower number arriving after a higher one.
- **P1 Call events and stream.** SIP emitter, Valkey stream, ingester, `integration_events`, SSE stream with tickets and resume, event history API, live-tail page, metrics (I-34 to I-36). ## Decisions

The four open questions were answered by the user on 2026-10-25. They are recorded in `.procoder/ask/decisions.md` ("Integrations: distribution, recordings, SSO, click-to-call"). There are no open questions left.

1. **Distribution (decision 1).** Private apps per customer only. No Hello-hosted relay and no marketplace listings; the marketplace/vendor path is "not planned". Google domain-wide delegation stays a discouraged fallback; Entra uses a per-customer app registration.
2. **Recordings to CRMs (decision 2).** Opt-in per connector. Links are random 256-bit tokens, 30-day default TTL, revocable (I-45, I-53).
3. **SSO for synced users (decision 3).** Required. Synced users sign in only through their IdP (OIDC for Google/Entra, LDAP bind for AD-only sites); they have no local password and directory- and SCIM-synced accounts cannot fall back to one. At least one local break-glass admin must always exist and the system refuses to remove the last one (I-29, I-30, AC-10b, AC-10c).
4. **Click-to-call (decision 4).** Ring-first only, with the authority rules in I-37 and I-39 (auto-answer off, `user` credentials dial from their own extension only, operators/admins and allow-listed service accounts may dial for others, emergency numbers refused, destinations inherit the outbound routes plus rate limits).
