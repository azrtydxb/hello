## Problem

Customers text and message businesses, not extensions. Today Hello handles voice, and `sip-messaging` moves short texts between phones, but a customer who texts the main number, sends a WhatsApp message or types into the website gets nothing: no number can receive SMS, there is no WhatsApp or web chat, and there is nowhere for a team to see, share, assign and answer them. A business that wants these channels today buys a second product, with a second contact list, a second set of users and no link to its calls or queues.

Hello should offer a **unified inbox**: one conversation list across SMS/MMS, WhatsApp and website chat, answered from the web UI (and, for texts, from the Grandstream desk phones), assigned to people or queues with the same ACD rules as calls, tied to the phonebooks and CDRs, with the compliance basics (opt-out, consent, retention, deletion) built in rather than left to the operator.

## Users

- **Agents** (any user with a linked extension, including the `user` role) answer conversations assigned to them or sitting in their queues, from the web inbox or a desk phone.
- **Supervisors** (operator, admin) see every conversation, reassign, resolve in bulk, edit canned responses and read the metrics.
- **Administrators** connect provider accounts (their own), map each number to a route, configure the chat widget, set retention and AI, and handle opt-outs and erasure requests.
- **Customers** (external): text a number, message on WhatsApp, or use the widget. They never authenticate to Hello.
- **Operators of the platform** need metrics, audit, HA behaviour and abuse controls for the two unauthenticated surfaces.
- **Developers/integrators** receive `conversation.*` and `message.*` events through the integrations event bus and webhooks.

## Defaults chosen for open points

Changing one is a spec edit. Defaults 2, 3, 5, 6 and 9 were confirmed or changed by the user on 2026-10-25 (see "Decisions").

1. **Customer-owned accounts only.** No Hello-hosted SMS or WhatsApp relay, no shared sender numbers, no Hello Meta app (consistent with `integrations.md` decision 1). Hello stores the customer's credentials sealed with `secret.Box` (`HELLO_SECRET_KEY`), AAD per record.
2. **Provider order:** Twilio first, Telnyx second, then Bandwidth and Vonage later (M-3; approved 2026-10-25). All sit behind one `SMSProvider` interface, so order is a delivery choice, not an architecture one. Before go-live the customer starts A2P 10DLC brand and campaign registration (and toll-free verification if wanted) in their own provider account; Hello only reports the state.
3. **Not a campaign tool.** No bulk sends, no scheduled sends, no import-and-blast, ever. First contact to a number with no prior inbound is off by default; when an admin turns it on, every such message needs an attested consent and is rate limited (M-17; approved 2026-10-25).
4. **Hello handles opt-out itself,** independent of what the provider does (M-16), so a provider that auto-blocks and one that does not behave the same.
5. **Bodies are stored in PostgreSQL as plain text** (database-volume encryption is the platform's job), with a full-text index; credentials are always sealed. Defaults: SMS/WhatsApp history 365 days, chat 90 days, media 90 days (M-19). Supervisor views of conversations are audited (M-21). Taken as recommended (2026-10-25).
6. **LAN-only; no public listener for now (user decision 2026-10-25).** The separate public listener (M-5: `/hooks`, `/chat`, `/m`) is **not now**, until the user decides. Consequences, plainly:
   - **No inbound SMS or MMS from Twilio or Telnyx by webhook,** so a provider number cannot receive texts in this build (polling could close that gap, see below; it is not scheduled).
   - **No delivery-status callbacks.** Outbound status is read by polling the provider's message resource (M-9a).
   - **No WhatsApp at all.** The Cloud API delivers inbound messages and statuses only by webhook, and the 24-hour window depends on inbound messages (section B).
   - **No public chat widget** on an Internet website. A LAN chat widget for intranet pages is built instead (M-28).
   - **No outbound MMS** to Twilio, Telnyx, Bandwidth or Vonage, because they fetch media from a public link (`/m/`, M-18). Outbound is text only.

   What works on the LAN: the inbox, outbound SMS text, texting from desk phones over SIP MESSAGE, inbound and outbound texts through a SIP trunk whose carrier carries SMS as SIP MESSAGE (M-4), the LAN chat widget, routing, AI and the privacy tooling. When the user enables the public listener later, the design in M-2, M-5, M-7, M-18 and section B applies unchanged.

   **Polling as an inbound path (checked 2026-10-25, not scheduled):** Twilio's "Read multiple Message resources" (`GET /2010-04-01/Accounts/{AccountSid}/Messages.json`, filters `To`, `From`, `DateSent`, `DateSent<`, `DateSent>`; records carry `direction: inbound` and `body`) **[verified]** (https://www.twilio.com/docs/messaging/api/message-resource). Telnyx `GET /v2/detail_records` with `filter[record_type]=messaging`, `filter[direction]=inbound` and a `created_at` range lists inbound messages **[verified]** (https://developers.telnyx.com/api-reference/detail-records/search-detail-records), but the detail record has no text (https://developers.telnyx.com/docs/messaging/messages/message-detail-records), so each body needs `GET /v2/messages/{id}`, which only works for messages up to 10 days old (https://developers.telnyx.com/api-reference/messages/retrieve-a-message); that it returns inbound bodies is **[unverified]**, and Telnyx recommends webhooks over polling. WhatsApp Cloud API: no list endpoint for inbound messages was found **[unverified]**. Bandwidth and Vonage: not checked **[unverified]**. `Reconcile(since)` (M-25) is this poll; with it, Twilio (and probably Telnyx) numbers could receive texts LAN-only, with a delay of the poll interval and media only for Twilio. It is designed and available, but **not scheduled**: enabling it as the inbound path is a user decision.

7. **SSE, not WebSocket,** for live updates (agent inbox and visitor widget): resumable with `Last-Event-ID`, proven in this codebase (`api/ai_stream.go`), passes the existing nginx with a dedicated location.
8. **Message content is not exposed to MCP or the AI assistant** (`x-hello-mcp: {"exclude": "customer message content"}`); statistics endpoints may be.
9. **AI is suggest-only first** (triage and draft). Auto-reply is off by default, enabled per number by an admin, answers only from admin FAQ snippets, at most 3 replies per conversation, discloses itself, and goes through the existing private-endpoint guard (M-30, M-30a; approved 2026-10-25).
10. **Viewer role has no access to message bodies.** Agents are defined by queue membership and extension links, not by role.

## In scope

### A. Providers

- [M-1] **`internal/messaging/provider`.** One interface, one registry; adding a carrier is one file and a golden-payload test.

  ```go
  type SMSProvider interface {
      Kind() string                                   // twilio | telnyx | vonage | bandwidth | sip_trunk
      Caps() Caps                                     // MMS, MaxBody, MaxMedia, MaxMediaBytes, StatusCallbacks, OptOut (provider|self), Reconcile
      Validate(ctx context.Context, cfg Config) error // on save: credentials work, numbers listable
      Send(ctx context.Context, m Outbound) (Sent, error)
      ParseWebhook(r *http.Request, cfg Config, raw []byte) ([]Event, error) // verifies the signature; returns normalised events
      FetchMedia(ctx context.Context, ref MediaRef) (io.ReadCloser, error)   // authenticated download
      Numbers(ctx context.Context) ([]Number, error)                         // optional: import DIDs and capabilities
      Registration(ctx context.Context, n Number) (RegState, error)          // optional: 10DLC / toll-free state
      Reconcile(ctx context.Context, since time.Time) ([]Event, error)      // optional: pull missed events
      Redact(ctx context.Context, providerID string) error                   // optional: provider-side delete (M-20)
  }
  ```

  `Event` is normalised: `Type` (`message.in`, `message.status`), `EventKey` (unique per provider event, the idempotency key), `ProviderMessageID`, `From`, `To` (E.164), `Body`, `Media []MediaRef` (URL or id, content type, size when known), `Status` (`queued|sent|delivered|failed|undelivered`), `ErrorCode`, `At`. Raw payloads are never stored. `Outbound` carries Hello's own message id, which the provider adapter puts in the status-callback URL (`?m=<id>`) so a status event can always be matched to the row even if the provider's send response was lost (M-9a).

- [M-2] **Webhook endpoints** (public listener only; **not now, user decision 2026-10-25**, see Default 6): `POST /hooks/sms/{hookId}` per channel and `POST /hooks/whatsapp/{hookId}` (plus its `GET` verification). `hookId` is 128 random bits generated at channel creation and is a routing key, **not** the authentication: every request is authenticated by the provider's signature (M-3) and is rejected `403`, empty body, if it fails. The signature is checked over the **raw body** before parsing. An unknown `hookId`, a disabled channel and a bad signature are all answered identically (`404`-equivalent empty `403`) so the endpoint reveals nothing.

- [M-4] **SIP MESSAGE from SIP trunks** (provider kind `sip_trunk`). `sip-messaging` already carries SMS over SIP per trunk (`trunks.messaging`, `inboundTrunkMessage`, `sendExternal`). The adapter lets a DID on such a trunk be a **channel address** so its texts enter the inbox instead of going straight to one extension.
  - Support depends on the **carrier**; no carrier is named as supported here. Which carriers deliver inbound SMS as SIP MESSAGE to a registered or IP-authenticated trunk, and whether they accept outbound MESSAGE for SMS, is **[unverified]**: no official documentation of a specific carrier was found in this research. The feature ships behind the existing per-trunk `messaging` flag with a lab checklist (send, receive, long text, non-ASCII, delivery behaviour, STOP behaviour) and is documented as "works only where your carrier supports it".
  - Hard facts: RFC 3428 limits a MESSAGE outside a media session to **1300 bytes** [verified, https://datatracker.ietf.org/doc/html/rfc3428 section on size]; so the adapter splits outbound bodies on a UTF-8 boundary at 1000 bytes, and refuses media (no MMS over this path). There are no delivery receipts: status is `sent` when the trunk answers 2xx and never `delivered`.
  - This is the **only inbound path from customers that works LAN-only** in this build (Default 6), so it is delivered early (Phase 3).
  - Inbound hand-off: `inboundTrunkMessage` calls `ConversationGateway.InboundFromTrunk(...)` first; the gateway returns `handled=true` when the dialled number is a channel address, otherwise the existing extension delivery runs unchanged (compatibility: nothing changes for trunks not configured as channels).

Helm: a separate Service and Ingress host (`messaging.public.ingress.*`), separate from the UI ingress, with a NetworkPolicy that lets it reach PostgreSQL, Valkey and MinIO only. On kw today the UI is LAN-only (`hello.kw.watteel.lab`), so nothing internet-facing exists until the operator enables this listener and publishes the host; the docs say so.

### B. WhatsApp Business Cloud API (Meta), customer-owned app (not now, user decision 2026-10-25)

> **Not now.** WhatsApp needs the public listener: the Cloud API sends inbound messages and statuses only to a webhook, and the 24-hour window cannot open without inbound messages. M-6 to M-11 stay as the design for when the user enables the public listener.

- [M-6] **Channel configuration.** The customer creates a Meta app with the WhatsApp product, a WhatsApp Business Account and a phone number in their own Meta business portfolio (https://developers.facebook.com/docs/whatsapp/cloud-api/get-started [verified: test account and test number are created automatically; real numbers need registration]). Hello stores per channel: `phone_number_id`, `waba_id`, a **system-user access token** (sealed), the **app secret** (sealed; the HMAC key for payload validation), a generated **verify token** (shown once), and the Graph API version (configurable, default taken from the version Meta's current docs show at implementation time; the 2026 docs show `v23.0` in template examples **[verified]**). The system-user token procedure itself is **[unverified]** (the Meta page was not retrievable); the guide links the customer to Meta's current page.
- [M-7] **Webhook.** `GET /hooks/whatsapp/{hookId}` answers the subscription handshake: Meta calls with `hub.mode`, `hub.verify_token`, `hub.challenge`; Hello echoes the challenge only when the token matches (constant-time) **[verified for the GET parameters]** (https://developers.facebook.com/docs/graph-api/webhooks/getting-started). `POST` events carry `X-Hub-Signature-256: sha256=<hex>`, an HMAC-SHA256 of the raw body with the **App Secret**; Hello validates it before parsing and answers `200 OK` to every authentic event **[verified]**. Failed deliveries are retried by Meta with decreasing frequency for **36 hours** and the receiver must deduplicate **[verified]**. The subscribed field is `messages`, whose `value` holds `messages[]` (inbound; `id` is the `wamid...` message id, `type`, `text.body`, media ids) and `statuses[]` (outbound `sent|delivered|read|failed`) **[verified from Meta's webhook components page]**: https://developers.facebook.com/docs/whatsapp/cloud-api/webhooks/components . Template review results arrive as `message_template_status_update` **[verified]**, https://developers.facebook.com/docs/whatsapp/business-management-api/message-templates .
- [M-8] **The 24-hour customer service window** **[verified]** (https://developers.facebook.com/docs/whatsapp/cloud-api/guides/send-messages): when a user messages (or calls) the business, a 24-hour timer starts and resets on each further user message; while open, free-form "service messages" (text, image, audio, document, interactive and so on) may be sent; after it closes **only approved template messages** may be sent. Business-initiated messages require the user's opt-in **[verified]**.
  - Hello keeps `conversations.window_expires_at = last_inbound_at + 24 h` for WhatsApp (and NULL for other channels). The composer and the API enforce it: a free-form send after expiry is refused `422 window_closed` **before** any call to Meta, and the UI switches the composer to the template picker. The provider's own rejection of a send that races the boundary maps to the same error. The exact Meta error code for this case is **[unverified]** (recalled as `131047`); the adapter maps by documented code once confirmed in N2 and otherwise by "any rejection of a free-form send whose window Hello believes closed".
  - Free entry-point windows (click-to-WhatsApp ads) exist per Meta's pricing page **[verified that they exist]**; Hello does not model them, it simply relies on the 24-hour rule it computes and on Meta's rejection if stricter.
- [M-9] **Templates.** Per channel, `wa_templates` mirrors the WABA's templates (name, language, category `MARKETING|UTILITY|AUTHENTICATION` **[verified]**, status, components JSON, Meta id), refreshed by list call on demand and by the `message_template_status_update` webhook. Admins can create and submit templates (`POST /{waba_id}/message_templates`, **[verified]** path shape in Meta's examples) and delete them; Hello never auto-submits. An agent sends a template into a conversation by choosing it and filling its variables; Hello validates variable count and refuses unapproved templates. Template sends are billed by Meta per message from 1 July 2025 **[verified]** (https://developers.facebook.com/docs/whatsapp/pricing); Hello shows the template category next to the send button and states nothing about prices. No template broadcast: one template send is always inside a single conversation.
- [M-10] **Limits to surface** (read-only in the channel page, from `GET /{waba_id}?fields=...messaging_limit_tier` style reads, field name `messaging_limit_tier` **[verified]**): a new business portfolio starts at a limit of **250** unique users outside a service window per rolling 24 hours **[verified]**; Hello shows the tier and warns at 80 percent of what it has itself sent outside windows.
- [M-11] **Media and ids.** Inbound media arrives as a **media id**; Hello resolves it to a URL and downloads with the bearer token. The id is available for **7 days** from the webhook and the resolved URL is valid for **5 minutes** **[verified]** (https://developers.facebook.com/docs/whatsapp/cloud-api/reference/media), so the fetch job runs immediately and retries only inside those bounds; a miss marks the attachment `expired` and the message stays. Size limits per the media reference **[verified]**: images 5 MB, audio 16 MB, documents 100 MB, animated stickers 500 KB; video **[verify the exact cap in N2]**. Outbound media is uploaded with `POST /{phone_number_id}/media` **[verified]** and sent by id, so no public URL is needed for WhatsApp. Read receipts and typing indicators exist on the API **[verified]**; Hello marks inbound messages as read when an agent opens the conversation, behind a channel switch (default on).

### C. Unified inbox

- [M-12] **Conversation model.** One **conversation** per (channel address, peer) while it is open; a **peer** is an E.164 number (SMS, WhatsApp `wa_id` normalised to E.164) or a chat visitor id.
  - States: `open`, `pending` (waiting on the customer), `snoozed` (until a time), `resolved`, `spam`. A new inbound message on a `resolved` conversation reopens it if the last activity is under `reopen_days` (default 7), otherwise starts a new conversation (history of earlier ones for the same peer stays linked through `peer_key`).
  - Fields: assignee (user), queue, priority (`low|normal|high`), tags, `last_message_at`, `last_inbound_at`, `first_response_at`, `resolved_at`, `window_expires_at`, unread counters per user in `conversation_reads`.
  - Messages: direction `in|out`, `note` (internal, never sent), `system` (assigned, resolved, opted-out and so on). Sender kind `customer|user|ai|system`. Status for outbound: `queued|sending|sent|delivered|read|failed|unknown`.
  - Everything is keyed by ids that survive a replica switch; nothing is held only in memory.
- [M-13] **Assignment (ACD reuse).** Control-side service `internal/messaging/router` (no SIP involvement).
  - An address's route (M-14) names a **queue**. A queue gains `text_enabled` (default false), `text_capacity` (concurrent open conversations per agent, default 3, 1 to 50) and `text_reassign_seconds` (default 300; 0 disables). Existing voice queues are untouched.
  - Candidates are the queue's members whose extension is linked to a **user** (`user_extensions`), who are `Staffed` per `queue.Member.Staffed(queue, state, known)` using the agent state already in Valkey (logged in for dynamic members, not paused), who have fewer than `text_capacity` open assigned conversations, and (optional queue flag `text_requires_idle_voice`, default false) are not on a call. Ordering uses `queue.Plan(strategy, cands, rr, seed)` with `Calls` and `LastEnd` taken from text assignments (a separate counter key, so voice statistics are not skewed). `ring_all` means **shared pool**: the conversation stays unassigned, visible to every candidate, and the first to open-and-reply claims it. Every other strategy assigns to the first planned agent immediately.
  - **Claim and assign are compare-and-set in PostgreSQL** (`UPDATE conversations SET assignee_user_id = $u WHERE id = $c AND assignee_user_id IS NULL`), with a per-agent `pg_advisory_xact_lock` while counting capacity, so two control pods or two agents cannot both win.
  - **No agent available:** the conversation stays unassigned in the queue's waiting list (oldest first) and an assignment sweep (woken by `pg_notify` on agent login, resolve or capacity change, plus a 10 s tick under `TryLock`) assigns as agents free up. Position and wait time are visible to supervisors.
  - **Reassign:** a conversation with an unanswered inbound message past `text_reassign_seconds` returns to the pool and is offered to the next planned agent (history row in `conversation_assignments`). Manual reassign to any user or queue by supervisors; agents may hand over to another member of their queues.
  - Pause and login reuse the existing queue feature codes and API (`/api/v1/agents`, feature codes `*45`..`*48` in `00023`); the inbox adds a login/pause toggle that calls the same store (no second availability concept).
- [M-14] **Per-DID routing.** `channel_addresses` holds one row per number (SMS DID, WhatsApp number, chat site). Per address: `route_kind` (`queue`, `user`, `extension` (its linked user), `ring_group` (shared pool of its members' users), `ai_triage` (M-30, then queue), `inbox` (unassigned supervisor pool)), `route_target`, an **after-hours** action (reply with a text, route to another target, or nothing) evaluated by the time-conditions engine when that branch lands **[assumed contract]** and otherwise by a simple weekly schedule stored on the address, an optional auto-reply on first contact, the `HELP` reply text (M-16), `desk_phone_delivery` (M-26), `ai_mode` (M-30), and `enabled`. A number received for which no address exists is rejected `404` to the provider and counted (`hello_msg_inbound_total{result="unknown_address"}`).
- [M-15] **Contacts and phonebooks.** A conversation's peer is resolved with `phonebook.Key` and the same source order as caller-name lookup (extensions, the viewer's personal book, the group's named books, company book). The name is computed at **read time per requesting user**, never stored from a personal book: a personal contact names the peer only for its owner (the rule of `phonebooks-ptt` P-10 and the CDR `caller_name_source` rule). `conversations.peer_name` stores only a name from shared sources (or the name a chat visitor typed), with `peer_name_source` (`extensions|company|named|visitor|provider`, never a book id of a personal book). "Add to contacts" in the UI writes an entry to the company/named book (operator and above) or the user's personal book (self-service), and refreshes the name. The right-hand panel also shows the peer's recent CDRs (`GET /api/v1/cdrs?number=`) and, when `integrations` click-to-call has landed, a Call button (ring-first rule of that spec).
- [M-16] **Opt-out (STOP) and consent.** SMS/MMS only; WhatsApp users are handled by Meta's block mechanism and by the opt-in note below.
  - **Hello detects keywords itself** on every inbound SMS: the whole trimmed, case-folded body (punctuation stripped) equal to one of `stop, stopall, unsubscribe, cancel, end, quit` **[verified as Twilio's default set]** (configurable per address) records an opt-out in `sms_opt_outs(address_id, peer_key)`; `start, unstop` (and `yes` only for a pending double opt-in) record an opt-in; `help, info` sends the configured help text. A keyword only counts as the **entire message**; "please stop calling me at 5" does not opt out. Keyword text is also stored as a normal message (the agent sees it) with a system line "customer opted out".
  - **Provider-reported opt-outs** (Twilio send error `21610` **[verified]**, a Telnyx or Bandwidth equivalent **[unverified]**) set the same state so Hello's view converges with the carrier's.
  - **Enforcement:** every outbound path (agent send, canned reply, auto-reply, AI, desk-phone reply) checks `sms_opt_outs` in the same transaction that queues the message and again in the sender worker immediately before the provider call; a send to an opted-out peer is `422 opted_out` and the composer is disabled with a banner. Agents cannot override it; only a customer START or an admin "record verbal re-consent" action (audited, with a note) clears it.
  - **Confirmation message:** sent by Hello (once, plain text) when the provider's `OptOut` capability is `self`; skipped when it is `provider` (avoids a double reply). The text is per-address and defaults to a neutral sentence including the business name.
  - **Survives erasure:** opt-outs are kept as `HMAC-SHA256(HELLO_SECRET_KEY-derived key, E.164)` plus address id and timestamp when a peer is erased (M-20), so a deleted customer is not texted again. This is the only residue of an erased number.
  - **WhatsApp opt-in:** Hello records, per peer, `consent_source` (`inbound` when the user wrote first, `attested` when an operator asserts prior consent) and refuses a business-initiated template without one of them.
  - Not legal advice: the guide lists what the customer's carrier, CTIA and Meta policies require and points to each provider's own pages.
- [M-17] **First contact and sending rules (approved 2026-10-25).** A reply inside an existing conversation is always allowed (subject to opt-out and the WhatsApp window). A **new outbound conversation** (`POST /api/v1/inbox/conversations`) is allowed only when `messaging_settings.first_contact` is `attested` (default `off`); it then requires `consentAttestation: true` and a free-text `consentNote`, both stored and audited, and is rate limited (per user 20 per hour, per address 200 per day, configurable). Numbers on the opt-out list and numbers not E.164 are refused. One message, one recipient, one attestation: there is no list, import or multi-recipient form, ever. In the LAN-only build this is the only way to start an SMS conversation on a provider number.
- [M-18] **Media in MinIO.** Bucket: the existing media bucket, prefix `msg/<channel_id>/<yyyy>/<message_id>/<sha256>`; table `message_media`.
  - **Inbound:** the webhook transaction inserts `message_media(status='pending')`; a worker on any control pod claims it (`FOR UPDATE SKIP LOCKED`), downloads through the provider adapter using `internal/safehttp` (SSRF-safe: provider media URLs are public https hosts; redirects only to the same provider's media host; size capped by `HELLO_MSG_MEDIA_MAX`, default 16 MiB, and the channel's own cap), sniffs the content type with `http.DetectContentType` (the declared type is advisory and must agree on the class), checks the allowlist (`image/jpeg`, `image/png`, `image/gif`, `image/webp`, `audio/*`, `video/mp4`, `video/3gpp`, `application/pdf`, `text/vcard`, `text/plain`), stores to MinIO with the SHA-256 and marks `ready`; otherwise `rejected` with a reason. The message is visible immediately; attachments show "downloading".
  - **Serving:** `GET /api/v1/inbox/media/{id}` (and the `/me` form) streams from MinIO after the same authorization as the conversation, with `Content-Type` from the sniffed type, `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment` for everything except images and audio/video previews, and `Cache-Control: private, no-store`. Never served from the public listener except through M-18's outbound token.
  - **Outbound (not now for SMS providers, user decision 2026-10-25):** needs the public `/m/` link below, so the LAN-only build sends text only and the composer hides attachments on SMS-provider addresses. An agent uploads (`POST /api/v1/inbox/media`, multipart, same allowlist and size checks, stored with `status='ready'`, unattached until sent, garbage-collected after 24 h if unused). For providers that need a fetchable URL (Twilio, Telnyx, Vonage, Bandwidth) Hello mints a **short-lived public link** `https://<HELLO_MSG_PUBLIC_URL>/m/<token>`: 256 random bits, only the SHA-256 stored, valid 15 minutes and at most 5 uses, `Cache-Control: private, no-store`, exactly the pattern of `integrations.md` I-45. WhatsApp uses the media upload endpoint instead (M-11). A message over a provider cap is refused before queueing with the cap in the error.
  - Transcoding is not provided; the UI warns when a file exceeds the smallest cap of the channel's provider.
- [M-19] **Storage, retention (approved 2026-10-25).** Tables in "Data". Bodies are plain text with a GIN full-text index (`to_tsvector('simple', body)`) for inbox search. Retention is per channel kind: messages and conversations 365 days (SMS, WhatsApp) / 90 days (chat) after `resolved_at` or last activity, media 90 days, configurable 1 to 3650; a purge job runs under `TryLock` on one replica, in batches of 500 conversations, deletes MinIO objects first and the rows after, and records counts only. Open conversations are never purged by age. `messaging_settings.retention_*` changes apply at the next run.
- [M-20] **GDPR / erasure and export.**
  - **Erase a peer:** `POST /api/v1/inbox/erase` `{channelId?, peer}` (admin; `peer` an E.164 or visitor id, or `conversationId`) deletes every conversation, message, note, media object (MinIO delete, verified by a follow-up `Stat`) and visitor record for that peer across all channels in one transaction plus the object deletions, replaces the audit detail with counts, keeps only the opt-out hash (M-16), and returns a report: rows and objects deleted, and per provider whether `Redact` succeeded. Provider-side deletion (Twilio message/media delete, Meta media delete **[verified that the Media API has DELETE]**) is best effort and reported; the customer's provider retains its own logs under their own terms and Hello says so in the report and the guide.
  - **Export (DSAR):** `GET /api/v1/inbox/export?peer=` (admin) streams a zip: `conversations.json`, one file per message with timestamps and status, and the media files; the audit row records who exported and the counts.
  - **Backups:** erased rows persist in database backups until the backups expire; the guide states this and recommends a backup retention no longer than the longest erasure SLA.
  - Agents' own deletion rights: an agent may delete an **internal note** they wrote; they cannot delete customer messages.
  - AI: no message content is stored by Hello at the AI provider by design; with a public endpoint enabled the customer's own policy applies (M-30).
- [M-21] **Audit.** Config changes use the existing `configChange` audit (channels, addresses, queues' text settings, templates, sites, retention, AI). Additional rows with actor, target ids and **no content**: credential set/rotated (never the value), channel enabled/disabled, opt-out recorded manually, `conversation.supervisor_view` (an operator or admin opens a conversation not assigned to them or their queues; one row per user and conversation per hour), export, erase, bulk resolve, reassign, AI auto-reply enabled/disabled and each AI auto-sent message (id only). Message bodies, phone numbers and visitor emails never appear in logs, metric labels or audit rows; logs carry conversation ids.
- [M-22] **Notifications.**
  - **Live:** the agent's inbox page holds an SSE stream `GET /api/v1/me/inbox/stream` (cookie session, same-origin `EventSource`; events: `conversation.new`, `conversation.assigned`, `message.in`, `message.status`, `conversation.updated`, `typing`; `id:` is a per-user monotonically increasing event id backed by the `conversation_events` table for 7 days so `Last-Event-ID` resumes; 15 s keepalive; dedicated nginx location with buffering off, like the AI stream). Cross-pod fan-out: PostgreSQL is the source of truth, Valkey pub/sub `hello:msg:user:<id>` only wakes the pod holding that stream, which then reads new rows by id.
  - **Browser:** the Notifications API when the tab is open and permission is granted (title and "New message from <name or number>", no body unless the user enables it in profile), an unread badge in the nav and the page title, and a short sound toggle.
  - **Email:** via the `user-accounts` mailer when the user has an email and no stream connection for 2 minutes: an unassigned-pool arrival or an assigned message, throttled to one email per conversation per 15 minutes, **without the message body by default** (per-user opt-in to include it).
  - **Desk phone:** M-26.
  - **Web Push** (service worker, VAPID) is out of scope for now (needs a new dependency and a public service worker); revisit on demand.
- [M-23] **Events and webhooks.** Through the integrations event pipeline when it exists (I-34 to I-42): `conversation.created`, `conversation.assigned`, `conversation.resolved`, `message.received`, `message.sent`, `message.status`, `message.optout`. Payload: ids, channel kind, direction, status, timestamps, assignee, queue, `peerKey` hashed unless the webhook endpoint has `includePeer: true`; **bodies and media are never included** unless the endpoint has `includeMessageBody: true` (admin, audited, off by default). Until the pipeline merges, `internal/messaging` emits through an `EventSink` interface with a no-op implementation, so the swap is one line.
- [M-24] **Canned responses and notes.** `canned_responses(id, scope[shared|user], owner_user_id, shortcut, title, body, channel_kinds)` with `{{name}}`, `{{agent}}` variables expanded client-side; notes are `note` messages visible to agents and supervisors only and never delivered.
- [M-25] **Idempotency and HA (inbound).** Both control pods serve the public listener behind the Service.
  1. Authenticate (M-2/M-7). 2. In **one transaction**: `INSERT INTO messaging_events (channel_id, event_key)` `ON CONFLICT DO NOTHING`; if the row was not inserted the event was seen: commit nothing else and answer 2xx. 3. Otherwise resolve the address, find or create the conversation (`INSERT ... ON CONFLICT` on the partial unique index "one open conversation per address and peer", which serialises two pods creating the same conversation), insert the message with `UNIQUE (channel_id, provider_message_id)` `ON CONFLICT DO NOTHING`, run STOP detection, insert pending media and a routing job, `pg_notify`. 4. Answer 2xx only after commit; if the transaction fails answer `5xx` so the provider retries (Telnyx, Bandwidth and Meta retry; Twilio behaviour on a failing webhook is **[unverified]**, so a reconciliation pull is provided: `Reconcile(since)` runs under `TryLock` every 5 minutes for providers that implement it and feeds the same ingest path, whose dedupe makes it safe). API shapes checked 2026-10-25: Twilio message list with `DateSent>` **[verified]**; Telnyx detail records plus per-message fetch within 10 days (Default 6). In the LAN-only build `Reconcile` is the only possible inbound path for provider numbers and is **not scheduled** (user decision).
  - `messaging_events` keeps 7 days. Status events for an unknown message are kept 10 minutes for a race with the send response, then dropped with a metric.
  - Workers (send, media, routing, reassign, AI, retention) run on every control replica and claim rows with `FOR UPDATE SKIP LOCKED`; leader-only tasks (reconcile, purge, SLA sweep) use `TryLock`. No in-memory state is required for correctness, so a control pod restart loses nothing.
- [M-9a] **Outbound sending semantics.** The composer posts `{body, mediaIds, templateId?, clientMsgId}`; `UNIQUE (conversation_id, client_msg_id)` makes a retried POST idempotent. The row is inserted `queued` in the same transaction as the opt-out, window and consent checks, then a worker sets `sending` (with an attempt id) and calls the provider.
  - The provider call is **at-most-once**: carriers do not offer an idempotency key Hello can rely on **[unverified for all four]**. Hello retries only when the failure is definite and pre-acceptance (connection refused, DNS failure, HTTP 429/503 before a body, with backoff 5 s, 30 s, 2 min, 3 attempts). If the worker dies or the response is lost while `sending`, the status callback (which carries Hello's id, M-1) resolves it; if none arrives within 5 minutes the row becomes `unknown` ("may have been delivered") and the agent sees a Resend button.
  - **LAN-only status (no callbacks, Default 6):** a status poller under `TryLock` fetches each message in `sent` state by its provider id (Twilio Message resource `GET .../Messages/{Sid}.json` **[verified]**, Telnyx `GET /v2/messages/{id}` **[verified that it exists, 10-day limit]**) every `HELLO_MSG_STATUS_POLL_INTERVAL` (default 30 s, backing off to 10 minutes) until a final state or 48 hours. A send whose response was lost has no provider id; it becomes `unknown` after 5 minutes. A lookup by `To` and `DateSent` in the Twilio list may resolve it **[verified filters; matching on body is a heuristic]**, but Hello never resends on its own. This is deliberately conservative: a duplicate SMS to a customer is worse than a visible failure.
  - Per-address outbound rate limit (Valkey token bucket, default 1 message per second per long-code address, configurable per address because carrier throughput differs and is **[unverified]** per brand tier) orders the queue FIFO per address.

### D. Desk phones

- [M-26] **Texts on desk phones over SIP MESSAGE.**
  - **Delivery to the phone:** when a conversation on an address with `desk_phone_delivery` is assigned to a user whose extension has registered contacts, the router inserts a `messages` row (the `sip-messaging` queue) with `sender_kind='external'`, `sender` the peer's E.164, `sender_name` the name resolved for **that user** (their own personal book allowed, same rule as M-15), `recipient` the user's primary extension, `scope='direct'`, and a new nullable column `conversation_message_id` linking it back. The body is prefixed `[WhatsApp] ` for non-SMS channels so replies are unambiguous. A `hello-sip` node delivers it by the existing claim/deliver loop to every registered contact; an unregistered phone gets it on next REGISTER within the queue's TTL. Chat visitors are not delivered (no number); a one-line alert ("New chat in Support, open the inbox") is delivered instead when the user enables it.
  - **Reply from the phone:** a MESSAGE from an authenticated device whose `To` is an E.164 number or a number of a known peer goes to `ConversationGateway.OutboundFromDevice(ctx, ext, to, ct, body)` before the existing external-number path. The gateway picks, in order: (a) the most recently active open conversation assigned to that extension's user with that peer, (b) a channel address enabled for outbound from that extension (`channel_addresses.owner_extension_id`), else (c) `handled=false` and the existing SIP-trunk external path runs. A reply that the rules forbid (opted out, WhatsApp window closed, rate limit) is answered to the **phone** by a MESSAGE from `system` with the reason, and to the sender with `403`/`480`-style status as `sip-messaging` already maps refusals. Only text is accepted from a phone; MMS from a handset is not supported.
  - **Authority:** the sender is always the authenticated device's extension (`sip-messaging` rule: never the `From` header); a phone cannot reply as another user and cannot message a conversation it is not assigned to.
  - **Size:** bodies from a phone above 1300 bytes are refused by RFC 3428 sizing; long outbound texts to the phone are split into parts of at most 1000 bytes on UTF-8 boundaries, each prefixed `(1/3)`.
  - **Phone support:** Grandstream WP822/WP836 per `phone-feature-parity` S-8 (IM account `P22650 = 1`); this is **[verified in the repo spec, unverified on hardware]** and is covered by the lab list. Other vendors' SIP MESSAGE UI is **[unverified]**; the provisioning template adds a per-vendor `capabilities.sip_message` flag, and the UI hides the desk-phone option for an extension whose phones are all of vendors without it.
  - Per-user setting `deskphone_delivery` (`off|on`, default off) in profile, in addition to the address flag; both must be on.
- [M-27] **Provisioning.** No new phone configuration beyond S-8; the capability flag above and a `docs/provisioning.md` note.

### E. Live chat (website widget)

- [M-28] **Widget delivery.** **LAN chat widget first (user decision 2026-10-25):** the widget, frame and `/chat/v1/*` endpoints below are served by a LAN chat listener in hello-control (`HELLO_MSG_CHAT_LAN_ADDR`, default off), with its own `http.Server`, middleware, limiter keys and metrics, exposed through the existing LAN ingress host under `/chat/` (or a LAN host of its own). It serves only `/chat/*` and `/healthz`; the admin API is never reachable on it. It is for intranet pages on the LAN or VPN; `allowed_origins` must be LAN origins and the UI warns on a public-looking origin. Every abuse control of M-29a applies unchanged (a LAN is not trusted). The same code moves to the public listener when the user enables it; the **public widget is not now**. Served by Hello, versioned and cacheable:
  - `GET /chat/v1/widget.js` (about 10 KB, no dependencies, `Cache-Control: public, max-age=3600`, `Cross-Origin-Resource-Policy: cross-origin`) and a sandboxed UI document `GET /chat/v1/frame?site=<siteKey>`. Embedding is `<script async src="https://chat.example.com/chat/v1/widget.js" data-site="SITE_KEY"></script>`. The loader injects an `<iframe sandbox="allow-scripts allow-same-origin allow-forms allow-popups" src=".../chat/v1/frame?...">` positioned by the loader; open/close, unread count and size cross the boundary by `postMessage` with strict `event.origin` checks both ways. The chat UI runs on Hello's origin so the host page's scripts and CSS can neither read it nor break it, and API calls from the iframe are same-origin (no CORS surface on the API).
  - **Per-site CSP:** the frame response carries `frame-ancestors <site.allowed_origins>` (empty list means `'none'` until configured), `default-src 'none'`, `script-src 'self'`, `style-src 'self'`, `connect-src 'self'`, `img-src 'self' data:`, `base-uri 'none'`, `form-action 'none'`. This stops browser embedding on unlisted origins. It does **not** stop a scripted client from calling the API directly (anyone can run `curl`), so the abuse controls below never rely on `Origin`.
  - Site settings: name, site key (public, random 96 bits, not secret), allowed origins, greeting, theme (accent colour, position, logo from MinIO), collect name/email (off, optional, required), business hours (same schedule type as M-14), offline mode (`collect` or `hidden`), default route (queue), pre-chat attributes, attachments allowed (default off), `retention_days`, abuse settings (below).
  - **Visitors are anonymous.** A visitor has no account; Hello stores a random `visitor_id` and the hash of a 256-bit **visitor token** held in the iframe's `localStorage` (partitioned by top-level site in current browsers, so persistence is per embedding site; if storage is blocked the visitor still chats for the session). The token authenticates every widget call and is never placed in a URL.
- [M-29] **Public chat endpoints** (all under `/chat/v1`, JSON, `Content-Type` enforced, 16 KiB body cap, `Cache-Control: no-store`):
  - `POST /session` create or resume (site key, optional visitor token, challenge solution (below), optional name/email, page URL and referrer as hints, truncated to 500 chars and stored only as hostname plus path), returns `{visitorToken, conversationId?, config}`.
  - `GET /events` SSE (visitor token in `Authorization` via `fetch` streaming, not in a URL; `Last-Event-ID` resume from `conversation_events`; 15 s keepalive; 1 stream per visitor, 2000 per control pod, closed after 30 minutes idle).
  - `POST /messages` `{text, clientMsgId}` (idempotent on `clientMsgId`), `POST /typing`, `POST /attachments` (only when enabled), `POST /end` (visitor closes), `GET /history`. Agent typing, "read" and delivery arrive over `/events`.
- [M-29a] **Abuse controls.** Layered, all server-side, all with metrics and an admin kill switch (`webchat.enabled` per site and global `HELLO_MSG_CHAT_ENABLED`):
  1. **Challenge at session creation:** per site `challenge` is `pow` (default: a stateless proof-of-work, SHA-256 over a server-signed nonce with difficulty tunable 14 to 22 bits, so no third party is involved), `turnstile` (customer-owned Cloudflare Turnstile site and secret key, token verified server-side against `https://challenges.cloudflare.com/turnstile/v0/siteverify`, tokens valid 300 s and single use (a replay is rejected as `timeout-or-duplicate`) **[verified]**, https://developers.cloudflare.com/turnstile/get-started/server-side-validation/ ; the call goes through `safehttp`), or `none` (explicit admin choice, warned in UI). Difficulty rises automatically for an IP or site under attack (adaptive step in M-29a.3).
  2. **Rate limits** (Valkey token buckets using the existing `Limiter` pattern; the client IP comes from the trusted-proxy logic already used by the API, never a raw `X-Forwarded-For`): session creation 5 per minute and 30 per hour per IP, 200 per minute per site; messages 20 per minute and 300 per day per visitor; per site 10,000 messages per day; attachments 5 per hour per visitor. Over limit: `429` with `Retry-After`, never a body that explains the rule.
  3. **Caps:** body 2000 characters (UTF-8 valid, control characters stripped, normalised), at most 1 open conversation per visitor, at most 200 visitor messages before any agent reply, at most `site.max_open_unassigned` (default 200) unassigned open chats per site; beyond that the widget switches to offline mode (collect contact, no live queue entry). Adaptive step: more than 3 times the median session rate for 60 s raises the challenge difficulty one level for 15 minutes and increments `hello_chat_challenge_raised_total`.
  4. **Blocklist:** agents click "Block visitor" (visitor id, and the hashed IP for `ttl` default 24 h, max 30 days); blocked sessions get a normal-looking `200` with a closed state, not an error. IPs are stored only as `HMAC-SHA256(daily salt, ip)` so logs and tables cannot be used to track visitors beyond the day (the salt rotates at 00:00 UTC; blocks keyed on the hash therefore expire at most by the day unless the admin pins a block by visitor id).
  5. **Content:** messages are plain text everywhere. The agent UI renders with text nodes only (never `innerHTML`), URLs are linkified by the UI with `rel="noopener noreferrer nofollow"` and a "leaves Hello" interstitial for the first click per link host; the optional site flag `strip_links` (default off) replaces URLs from visitors with `[link removed]`. Honeypot field in the session request (any value rejects silently).
  6. **Attachments** (off by default): images and PDF only, 5 MB, magic-byte sniff, stored in MinIO, served to agents with `attachment` disposition and `nosniff`; no antivirus component is bundled, so the setting says so and recommends leaving it off for open sites.
  7. **Privacy:** no third-party cookies, no fingerprinting; `User-Agent` stored as a coarse family only; the widget shows the retention period and a link to the site's privacy policy URL (setting) and records `consent_to_store` when "collect name/email" is on.
  8. **Resource:** public handlers run with a request deadline of 10 s, a per-pod concurrency limit (default 500 in flight, then `503`), and never block on provider calls; the public listener has its own `http.Server` timeouts (header 5 s, idle 60 s, write deadline cleared only on `/events`).
- [M-29b] **Offline and email** (works LAN-only as long as the SMTP server is reachable). When no agent is available or the site is outside hours, the widget collects name, email and message; the conversation is created `open`, unassigned, flagged `offline`, and an agent can **reply by email** (using the `user-accounts` mailer and `smtp_settings`) to the address given; the email contains the reply text and no link that needs authentication. A visitor who returns with the token sees the reply in the widget. Emailing requires `smtp_settings` to be configured (the UI disables the reply-by-email button otherwise). Inbound email replies are out of scope.
- [M-29c] **Transcripts.** A visitor may request a transcript by email at the end of a chat (off by default, sends to the address they typed, rate limited 3 per day per visitor).

### F. AI

- [M-30] **AI features, only through `internal/ai` (approved 2026-10-25: suggest-only triage and drafts first).** No new model client: every call is `ai.Generate[T]` (go-ai-sdk, built in `internal/ai/provider.go`). The feature is off unless `internal/ai` is enabled and the channel address has `ai_mode` ≠ `off`. Customer message content therefore goes only where the existing privacy guard allows (private endpoint, or `HELLO_AI_ALLOW_PUBLIC_ENDPOINT=true`); the inbox shows "AI endpoint is public" in settings when so.

  - **Triage output (structured):** `{language, intent (from an admin list or "other"), urgency low|normal|high, sentiment, spam bool, summary (≤ 280 chars), suggestedQueue?, suggestedTags[], handoffRecommended bool}`. Applied by the router as suggestions (tags, priority, queue) with actor `ai`, never changing assignment of an already-assigned conversation, and visible/revertible in the UI; `spam` only sets a flag for supervisors (it does not delete or auto-block).
  - **Draft:** one suggestion per inbound message batch, shown in the composer as a dimmed proposal; the agent must click to use it; sending is by the agent, so audit shows the user.
  - **Inputs:** the current conversation (last 20 messages, 8 KB cap), the customer's first name when known from shared books, the address's FAQ snippets, the business name. No other conversations, no CDRs, no config, no other customers. Optional `ai_redact` (default on) replaces phone-number-like digit runs of 7+ and email addresses with placeholders before the call. Customer text is delimited as untrusted data in the prompt; the model has **no tools that change anything**: only `lookup_faq(query)` (read-only over the address's snippets) and `handoff(reason)` (flags for a human). Output is schema-validated and rejected on mismatch.
  - **Where it runs:** after the ingest commit a row is inserted in `ai_message_runs` (one per inbound message, `UNIQUE (message_id, kind)`); any control replica claims it (`SKIP LOCKED`), applies the existing limiter/budget (`internal/ai/limits.go`), calls `ai.Generate`, and stores the result. A result is discarded if the conversation moved on (compare-and-set on `last_message_id`, so a human reply or a newer inbound wins). A failure never delays or blocks delivery of the customer's message to a human; it records `error` and moves on.
  - Metrics `hello_msg_ai_runs_total{kind,result}`, tokens through the existing AI usage.
- [M-30a] **Auto-reply guardrails** (mode `auto`, off by default, enabled per number by an admin, audited; approved 2026-10-25; the private-endpoint guard of `internal/ai` applies to it as to triage):
  - Grounded in the address's **FAQ snippets** (≤ 50 per address, ≤ 4 KB each, admin-authored); if the answer is not supported by a snippet the AI must call `handoff`. A reply may contain a URL only if that exact URL is in a snippet.
  - At most **3** AI replies per conversation (configurable 1 to 10), then a human must reply; a customer message containing a handoff word (`agent`, `human`, `person`, `representative`, configurable) or an opt-out keyword or `HELP` never triggers AI; messages classified `urgency=high` or `sentiment` negative go to a human immediately with an automatic holding line.
  - Never on WhatsApp outside the 24-hour window (the window rule applies to AI exactly as to agents), never to an opted-out peer, never when an agent has replied in the last 10 minutes, never for `spam`.
  - Every AI message is stored with `sender_kind='ai'`, labelled in the UI, and, when `ai_disclosure` is on (default on), the first AI reply to a conversation starts with the configured disclosure line. (Disclosure may be a legal requirement in some jurisdictions **[unverified]**; the setting exists for that reason.)
  - Per-address cap of AI sends per hour (default 60) and a global kill switch `HELLO_MSG_AI_AUTO=false`.

## Constraints

- No PostgreSQL call is added to the SIP **call** path. The messaging gateway runs on the `MESSAGE` path only, which `sip-messaging` already allows to use PostgreSQL (its durable queue); the gateway adds at most one indexed lookup and one insert per phone-originated reply.
- hello-control is the only component that talks to providers, Meta, Turnstile and the AI endpoint; hello-sip never calls any of them.
- Public surfaces (`/hooks`, `/chat`, `/m`) share nothing with the admin API except the store; they have their own server, middleware, limiter keys and metrics.
- Secrets (provider tokens, app secrets, Turnstile secret, webhook verify tokens) are sealed with `secret.Box`, returned only as `has*` booleans, absent from logs, audit rows, metrics and the AI.
- Outbound HTTP to providers uses `internal/safehttp` with a per-adapter host allow-list (the provider's API and media hosts), no redirects off that allow-list, response caps (64 KiB for sends, `HELLO_MSG_MEDIA_MAX` for media), timeouts 10 s (30 s media).
- Message content is never in logs, metric labels, traces or audit rows. Conversation ids and counts are.
- No new Go dependencies planned: stdlib `crypto/hmac`, `crypto/ed25519` (Telnyx), `crypto/sha256`, `net/http`, existing minio-go, Valkey and Postgres clients; JWT verification for Vonage and Bandwidth uses a small in-tree HS256 verifier (≈ 60 lines) unless review prefers `github.com/golang-jwt/jwt/v5`, to be decided when Bandwidth or Vonage is built. The widget is hand-written TypeScript compiled into a single static asset by the existing web build (no framework in the widget).
- Performance: ingest of a webhook (verify, one transaction, 2xx) p99 under 100 ms excluding media, so Telnyx's 2 s and Bandwidth's 10 s bounds are never at risk; inbox list p99 under 150 ms for 100,000 conversations (indexes below); SSE delivery of a new message to a connected agent under 1 s p95.
- Compatibility: nothing changes for deployments that do not configure a channel: the public listener is off, new tables are empty, `sip-messaging` behaviour is identical for numbers that are not channel addresses.
- Deployment: kw via Kuvryn Sync; no workloads on the user's Mac; CI on the Arc runners. Provider adapters are tested against local fake servers; real-account checks are lab items (below) and never block merge.
- Gate per task: gofmt, `go vet`, golangci-lint (0), `go test -race ./...`, `procoder check` 0 blocking, mutation checks, web lint and tests; REVIEW.md applies; no AI attribution in commits.

## Edge cases

- The same SMS delivered twice by a provider or by two pods: second insert hits `messaging_events` or `UNIQUE (channel_id, provider_message_id)` and is a no-op with `2xx`.
- Two pods create a conversation for the same new peer simultaneously: the partial unique index makes one insert win; the other attaches to it.
- An inbound message arrives for a number no longer configured: rejected to the provider, counted; no conversation is created.
- A message with `NumMedia=3` and one media download failing: the message and the other two attachments stay; the failed one is `expired` or `rejected` with a reason.
- Non-GSM characters: segment counter in the UI follows UCS-2 rules (70/67 characters per segment vs 160/153) **[standard SMS, not provider-verified]**; the provider splits, Hello stores one message.
- An agent replies on SMS while the peer is opted out: refused before queueing; the UI shows the banner. The same peer texts START: opt-in recorded, banner clears, thread continues.
- A WhatsApp message arrives at 23:59:59 of the window and the agent replies 1 s later: Hello's calculation allows it; if Meta rejects, the message goes `failed` with the mapped reason and the template picker is offered.
- A WhatsApp conversation idles 24 h with the agent mid-typing: the composer flips to template-only at expiry (client timer plus server check).
- A peer exists on SMS and WhatsApp with the same number: two conversations (different addresses); the desk-phone prefix disambiguates replies; the right panel links them as "other conversations with this contact".
- A chat visitor clears storage: new visitor id, new conversation; the agent can merge two conversations by hand (supervisor action) when the visitor typed the same email.
- A visitor sends 500 messages in 10 s: rate limits answer 429; at the cap the widget shows "please wait for an agent".
- An agent logs out with 5 open assigned conversations: they remain assigned; after `text_reassign_seconds` of an unanswered inbound message each returns to the pool. Supervisors can bulk-reassign.
- A queue is deleted or text-disabled while conversations reference it: deletion is refused `409` while open conversations reference the queue; disabling returns them to the address's fallback route.
- An extension is unlinked from a user: that user disappears from candidate lists; assigned conversations are reassigned on the next sweep.
- A user is deleted: assigned conversations become unassigned; notes keep `sender_user_id` NULL with the display name at the time (`sender_name`).
- A phone replies to a number with three open conversations (different addresses): the most recently active one assigned to that user wins; if none is assigned to them the reply is refused with a MESSAGE explaining it.
- A time-conditions branch is not merged: after-hours uses the address's own weekly schedule; the two are exclusive per address once both exist (UI shows which is active).
- The widget is embedded in a page served from an origin not in `allowed_origins`: the browser refuses to render the frame (`frame-ancestors`); the loader reports `blocked` to the console only.
- An erase request for a number with an open conversation: allowed; the conversation is deleted immediately and a later inbound from that number starts fresh (the opt-out hash is the only remembered fact).
- The provider sends a status for a message Hello did not send (sent from the provider's console): recorded as an outbound message with `sender_kind='system'` and `via='provider'`, no routing.

## Failure modes

- **PostgreSQL unavailable:** (with the public listener) webhooks answer `503` (providers with retries redeliver; Twilio redelivery **[unverified]** so reconcile covers it), the public chat answers `503` with `Retry-After`, the inbox shows an error; calls are unaffected.
- **Valkey unavailable:** limiters fall back to per-pod memory (stricter, with a metric), SSE wake-ups fall back to a 2 s PostgreSQL poll, agent availability for assignment falls back to "static members only" for text, as queues already degrade.
- **MinIO unavailable:** the message text is stored and delivered; attachments stay `pending` and retry for 24 h; uploads are refused with `503`.
- **A provider is down or rejects credentials:** sends fail with a mapped reason; the channel status becomes `degraded` after 5 consecutive failures, an audit row and a UI banner appear, and nothing is retried beyond M-9a's rules. A revoked token (HTTP 401) marks the channel `credentials_invalid` and stops sends instead of hammering.
- **Webhook signature secrets rotated:** during rotation (admin sets a new secret while keeping the old one for 24 h) both are accepted, as in `integrations.md` I-42.
- **A control pod dies mid-ingest:** the transaction rolled back; the provider's retry (or reconcile) redelivers. **Mid-send:** the row is `sending`; the status callback or the 5-minute sweeper resolves it to `sent` or `unknown` (M-9a).
- **hello-sip pod restarts during desk-phone delivery:** the `messages` row is `sending` and reclaimed per `sip-messaging`'s claim timeout.
- **Meta token expired or revoked:** channel `credentials_invalid`; the UI says which credential to renew; WhatsApp messages stay queued up to 1 hour, then fail.
- **AI endpoint down or over budget:** triage/draft are skipped silently (UI shows "no suggestion"); auto-reply falls back to the holding line configured for the address (if any) and flags the conversation for a human.
- **Public listener under attack:** per-pod in-flight cap returns `503`, challenge difficulty rises, supervisors can disable a site in one click and ops can set `HELLO_MSG_CHAT_ENABLED=false`; the admin API is unaffected because it is a different listener.
- **Clock skew:** Meta/Telnyx/Twilio signature timestamps are checked with a 5-minute tolerance where the scheme has a timestamp (Telnyx header **[verified]**); the WhatsApp window uses server time of the inbound receipt, not the provider's timestamp.

## Threat model (public surfaces)

In the LAN-only build the unauthenticated surface is the LAN chat listener (and SIP MESSAGE from authenticated devices and trunks); the webhook, media-link and WhatsApp rows apply when the public listener is enabled.

| Threat                                                   | Control                                                                                                                                                              |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Forged provider webhook                                  | Signature check over raw body before parsing (M-2/M-7); unknown/disabled/bad all look identical; `hookId` unguessable but not trusted                                |
| Replay of a captured webhook                             | Idempotency ledger; timestamp tolerance where available                                                                                                              |
| SSRF through attacker-influenced media URLs in a webhook | Only after a valid signature; `safehttp` with host allow-list per provider, no redirects off it                                                                      |

| Stored XSS in the agent inbox                            | Text-only rendering, no `innerHTML`, strict CSP on the console already, link interstitial                                                                            |
| Visitor token theft                                      | 256-bit random, only hash stored, header-only, short-lived resume (90 days idle expiry), `localStorage` in a Hello-origin iframe so host-page scripts cannot read it |
| Clickjacking / hostile embedding                         | `frame-ancestors` per site, `sandbox` on the iframe                                                                                                                  |
| Origin spoofing by scripts                               | Not relied on; documented                                                                                                                                            |
| Toll fraud via outbound SMS                              | First contact off by default, rate limits, opt-out, per-address daily caps, alert metric on unusual rates, optional destination country allow-list in settings       |
| Agent impersonation from a phone                         | Sender = authenticated device extension only                                                                                                                         |
| AI prompt injection                                      | Untrusted-data framing, no write tools, schema validation, FAQ-only grounding, URL allowlist, human handoff, kill switch                                             |
| Data exfiltration through AI                             | Only the current conversation in context, redaction on, private endpoint by default                                                                                  |
| Over-broad internal access                               | Ownership checks, supervisor-view audit, MCP exclusion, `viewer` none                                                                                                |

## Phased delivery

Each phase is one or a few PRs, independently mergeable, ships its migration, API, OpenAPI entries (and `x-hello-mcp` decisions), UI, tests, metrics, audit and docs (`docs/messaging.md`, `docs/provisioning.md` where noted), and leaves nothing half-wired (a feature is fully usable or unreachable). Each phase opens by re-reading the provider documentation it depends on and recording the result; **[unverified]** items it needs are resolved or their fallback is applied before it closes. Prerequisites: `user-accounts` merged (agents are users); `call-queues` merged (Phase 5); `integrations` P1/P2 are **not** prerequisites (the `EventSink` no-op carries until then); `sip-messaging` merged before Phase 3.

Order after the user's decisions of 2026-10-25: everything that can be built and tested on the LAN comes first.

1. **Inbox core.** Migration `messaging_core`; `internal/messaging` (models, store, opt-out engine, retention, erase, audit, events sink); scope `messages`; `/api/v1/messaging/channels|addresses|settings|optouts`, `/api/v1/inbox/*` and `/api/v1/me/inbox/*` (assignment by hand and `claim`, shared pool only); SSE stream; Inbox page, channels page, settings, opt-outs; notifications live + browser + email. The nav entry stays hidden until Phase 2 or 3 gives the inbox a channel.
2. **Outbound sending on Twilio.** `internal/messaging/provider` interface and the Twilio adapter (`Send`, `Validate`, `Numbers`, text only); send worker with M-9a semantics; status polling (no callbacks); first contact off by default and, when an admin turns it on, attested per message and rate limited (M-17); per-address throughput limit. Usable: an agent can text a customer and see delivery status. Before go-live the customer starts 10DLC/toll-free registration in their Twilio account.
3. **SIP MESSAGE: desk-phone texting and the SIP trunk channel.** `ConversationGateway` in `internal/sip`; migration `messaging_deskphone`; delivery of assigned conversations to desk phones and replies from them (M-26); the `sip_trunk` provider adapter and 1300-byte splitting (M-4), the first inbound path from customers that works LAN-only; contacts and phonebook mapping with "add to contacts" (M-15); vendor capability flag; profile setting; lab checklist for WP822/WP836 and for the SIP-trunk carrier(s).
4. **LAN chat widget.** Migration `messaging_webchat`; the LAN chat listener (`HELLO_MSG_CHAT_LAN_ADDR`) and its ingress path; widget build and embed for intranet pages; frame with per-site CSP; chat endpoints; SSE for visitors; challenge (pow; Turnstile only where the LAN can reach Cloudflare), limiter, caps and blocklist; offline mode and reply by email; transcripts; sites page.
5. **Routing and ACD.** Migration `messaging_routing`; per-DID route kinds (queue, user, extension, ring group, inbox), router with `queue.Plan`, capacity, reassign, waiting list, SLA metrics, agent login/pause in the inbox, after-hours (own schedule; time-conditions when present), queue text settings in the Queues page, supervisor views and stats.
6. **Telnyx and sender registration.** Telnyx adapter (send, numbers, status polling within its 10-day limit); `Registration` (10DLC/toll-free state) for Twilio and Telnyx and the compliance checklist panel. Bandwidth and Vonage come later, by demand, on the same interface (JWT decision, in-tree vs library, recorded then).
7. **AI.** Migration `messaging_ai`; `message_triage` and `message_draft` (suggest-only) first, then `message_autoreply` behind the M-30a guardrails (off by default, per number, FAQ-only, 3 replies, disclosure, private-endpoint guard); FAQ editor; kill switches; UI chips.
8. **Integrations, reporting and privacy tooling.** Events into the real pipeline and webhook options (`includePeer`, `includeMessageBody`); stats and reports (first response, resolution time, volume by channel/queue/agent, SLA breaches); DSAR export; provider-side `Redact` for adapters that support it; supervisor-view audit report; docs.

**Not now (user decision 2026-10-25), design kept:**

- **N1. Public listener and webhooks.** M-5 listener, Helm Service/Ingress/NetworkPolicy, `/hooks/sms/{hookId}` with `ParseWebhook` for Twilio and Telnyx, status callbacks, inbound media fetch, outbound MMS through `/m/{token}`, public chat widget.
- **N2. WhatsApp** (old P5, section B). Needs N1.
- **N3. Inbound SMS by polling** (`Reconcile`, Default 6). Possible without N1 for Twilio (and Telnyx within its limits); scheduled only if the user chooses it.

## Decisions (2026-10-25)

The open questions were answered by the user on 2026-10-25 and are recorded in `.procoder/ask/decisions.md`.

1. **Providers.** Twilio first, then Telnyx; Bandwidth and Vonage later. Before go-live the customer starts 10DLC (and, if wanted, toll-free) registration in their provider account; Hello only reports the state.
2. **Public access.** Not now. Build LAN-only; the separate public listener (`/hooks`, `/chat`, `/m`) is out of scope until the user decides. Consequence: inbound SMS by webhook, delivery-status callbacks, WhatsApp, the public chat widget and outbound MMS cannot work without it. The phases are reordered so LAN-testable work comes first (inbox core, outbound sending, SIP MESSAGE desk-phone texting and the SIP trunk channel, LAN chat widget). Polling for inbound messages is possible on Twilio **[verified]** and partly on Telnyx (text through a per-message fetch, 10-day limit, **[unverified]** for inbound bodies); it is noted (N3), not scheduled.
3. **Outbound first contact.** Off by default. When an admin turns it on, each message needs an attested consent and is rate limited. Never bulk.
4. **Storage.** Not put to the user; the recommendation is taken: plaintext bodies in PostgreSQL with full-text search, volume encryption, audited supervisor views, retention 365 days (SMS) and 90 days (chat, media).
5. **AI.** Suggest-only triage and drafts first. Auto-reply is off by default, enabled per number, answers only from admin FAQ snippets, at most 3 replies per conversation, discloses itself, and uses the private-endpoint guard.
