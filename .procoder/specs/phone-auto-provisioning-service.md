# phone-auto-provisioning-service

Status: approved

Source: `.procoder/backlog/milestones/phone-auto-provisioning.md` and its epic `phone-auto-provisioning-service`; `hello-pbx-spec.md` §6.4 (the console covers provisioning). Decided 2026-10-06 (`.procoder/ask/decisions.md`, "Remaining items after Phase 7"):

- **vendors:** Yealink, Poly, Grandstream, Snom and Fanvil are first-class (built-in templates, tested request paths); any other brand works through a generic per-model template system with admin-editable templates and variables
- **discovery:** all three — DHCP option 66 (Hello documents what the administrator sets), vendor cloud redirect (Yealink RPS, Poly ZTP, Grandstream GDMS, Snom SRAPS, Fanvil FDPS: Hello registers MACs with the vendor's redirect service when credentials are configured, each vendor a pluggable client, and everything works without them), and manual URL entry
- **authentication:** MAC plus a per-device unguessable token in the URL path, over HTTPS; a MAC allowlist (a phone must be pre-registered and assigned to an extension); rate limiting; an audit record of every fetch; token rotation

- **answered the same day (open questions of this spec, `.procoder/ask/answers.md`):**
  - certificate: kw's private `cluster-ca`, with Hello's CA pushed over plain HTTP (S-12)
  - phones found through DHCP: trust on first use; the first fetch from a pre-registered MAC hands out its token once, and an administrator can re-arm (S-10)
  - redirect services wired and live-tested on kw: Snom SRAPS, Yealink RPS/YMCS and Grandstream GDMS; Poly and Fanvil stay a manual step; credentials arrive as sops secrets, and the live tests run only when those secrets exist (S-11)
  - phone admin password: random per phone, stored encrypted, revealable by administrators (S-20)

## Problem

Every phone on Hello today is configured by hand: an administrator creates a device, copies its secret from a dialog that shows it once, and types server, port, domain, username and password into each phone's web UI (`docs/phones.md`). That is slow, error-prone and leaks secrets into chat and sticky notes, and it does not scale past a handful of desks. Every desk-phone vendor supports the same industry flow instead: the phone learns a provisioning URL (DHCP, a vendor redirect cloud, or one typed URL), downloads a common file and a per-MAC file over HTTP(S), and configures itself. Hello needs to be the server at the end of that URL: it must know which phone is which, render each vendor's file format from Hello's own data, hand out SIP credentials only to the phone that owns them, and show the administrator what every phone fetched and when.

## Users

- **Administrators:**
  - add a phone by MAC and model and assign it to an extension (or bulk-import a CSV), then plug it in and have it register with no typing on the phone
  - edit, preview and override the template a model uses, for any brand
  - upload firmware and pin a version per model
  - copy the DHCP option 66 value or a phone's own URL, and connect vendor redirect accounts
  - rotate a phone's token, retire a phone, and see every fetch it made
- **Phone users:** get a working desk phone, with their name on the screen and BLF keys for their colleagues, without knowing what SIP is.
- **Operators:** watch fetch rates, denials, rate-limit hits and redirect-registration failures in metrics, and trust that a stolen MAC address alone does not yield a SIP password.
- **Developers:** run the provisioning flow of every first-class vendor in the lab, byte for byte as the phones request it.

## In scope

- [S-1] **Phone inventory.** `/api/v1/phones` CRUD. A phone has a MAC (12 hex digits, stored lowercase, unique, accepted with `:`/`-`/`.` separators), an optional serial number (Yealink YMCS and Grandstream GDMS need it, S-11), a vendor (`yealink`, `poly`, `grandstream`, `snom`, `fanvil` or `generic`), a model (free text, e.g. `T54W`, `VVX 450`, `GRP2614`, `D785`, `X5U`), an optional label, the device it provisions (exactly one; see S-2), an optional template override, BLF keys (an ordered list of extension numbers), an enabled flag, and its fetch state: first and last fetch time, last source IP, last User-Agent, the last file served and the firmware version parsed from the User-Agent when the vendor puts it there. A phone is on the **allowlist** only while it is enabled and assigned to an enabled device of an extension; anything else is denied (S-6).
- [S-2] **Device binding and SIP credentials.** A phone provisions exactly one Phase 1 device. Creating a phone for an extension either creates a new device (SIP username `<extension>-<last 6 MAC hex>`) or binds an existing one.
  - Phase 1 stores only digest HA1 values, so the plaintext a phone needs cannot be recovered. A device bound to a phone therefore gets a **new secret, sealed** with `internal/secret` (AES-256-GCM under `HELLO_SECRET_KEY`, AAD `device:<id>`) in a new `secret_enc` column of `devices`, and its HA1 values are updated in the same transaction. Binding an existing device says so in the UI and API ("binding rotates the device secret; re-provision or re-type any phone already using it"), and the change is audited.
  - Rotating a provisioned device's secret (`POST /api/v1/devices/{id}/rotate-secret`) re-seals it; the phone picks the new secret up at its next fetch. Unbinding a phone drops `secret_enc` (the device keeps working with its HA1 values).
  - The sealed secret is opened only by the renderer, never returned by any API, and never logged.
- [S-3] **Provisioning tokens.** Each phone has a token: 32 random bytes, base32-lowercase without padding (52 characters). Hello stores its SHA-256 (lookup, unique, the way `auth.HashToken` stores API tokens) and the token sealed under `HELLO_SECRET_KEY` with AAD `phone-token:<id>` (needed to render the phone's own re-check URL and to register it with redirect services). The plaintext URL is shown once, on create and on rotation, like device secrets.
  - **Rolling rotation:** `POST /api/v1/phones/{id}/rotate-token` makes a new current token and keeps the old one valid as `previous` until the phone first fetches with the new token or a grace period passes (`HELLO_PROV_TOKEN_GRACE`, default 7 days). A fetch with the previous token is served normally, but the config it gets carries the new token in its provisioning URL, so the phone moves itself over. `?immediate=true` revokes the old token at once (a stolen-token response).
  - Redirect registrations (S-11) are updated to the new URL on rotation.
- [S-4] **The provisioning endpoint.** hello-control serves provisioning on a second listener, `HELLO_PROV_ADDR` (default `:8083`), separate from the management API. Request shapes:
  - `GET /p/<token>/<file>`: the per-device form. The token selects the phone; the requested file name is matched against that phone's vendor file set (S-7). A file name that embeds a MAC must embed this phone's MAC (case-insensitive), or the request is denied as `mac_mismatch`.
  - `GET /p/boot/<file>`: the DHCP bootstrap form, with no token (S-10). It never returns a SIP secret or the admin password, and it returns a token only in the single trust-on-first-use hand-off of S-10.
  - `GET /p/ca.crt`: Hello's provisioning CA certificate (public, PEM and DER by `Accept`/extension), so phones can be told to trust it (S-12).
  - `GET /p/<token>/fw/<file>`: firmware (S-13).
  - Phones that upload logs or overrides (`PUT /p/<token>/<mac>-app.log`, `PUT .../<mac>-phone.cfg` on Poly) get `204` and the body is discarded, length-capped at 1 MiB; uploads are not stored.
  - Responses carry `ETag` (a hash of the rendered body) and honour `If-None-Match` with `304`, so a phone's periodic re-check costs no render beyond the hash.
  - Anything else answers `404` with an empty body; denied requests answer `404` too (not `403`), so the endpoint does not confirm which MACs or tokens exist.
- [S-5] **What a rendered config carries.** For the phone's bound device: SIP username and auth name, the opened secret, the display name (the extension's name) and line label (the extension number), the registrar `HELLO_PROV_SIP_SERVER` (`host:port`, default `HELLO_SIP_ADVERTISED_ADDR`; on kw `192.168.10.101:30508`, the Kamailio NodePort), the SIP domain `HELLO_SIP_DOMAIN`, transport UDP (Hello is UDP-only), a registration expiry inside `HELLO_SIP_REGISTER_MIN/MAX_EXPIRES`; BLF keys pointing at `<number>@<domain>` (Phase 4 presence); the voicemail feature code for the message key; the time zone and NTP server from `HELLO_PROV_TIMEZONE` / `HELLO_PROV_NTP`; the phone's own provisioning URL (`https://…/p/<token>/`) and a periodic re-check interval (`HELLO_PROV_RESYNC`, default 24h, with jitter derived from the MAC); the CA certificate URL; and the firmware URL when a version is pinned for the model.
- [S-6] **Request authentication and the allowlist.** A per-device request is served only when all hold: the token matches a current or in-grace previous token; the phone is enabled and bound to an enabled device (allowlist); any MAC in the file name is the phone's; and the request arrived over HTTPS (TLS terminated by the ingress with `X-Forwarded-Proto: https` from a trusted proxy, or TLS on the listener). A per-device request over plain HTTP is refused (`plain_http`) and its token is treated as exposed: the phone is flagged `token exposed` in the UI so the administrator rotates it.
  - When the vendor's User-Agent carries a MAC (Yealink, Grandstream and Fanvil do; Poly does once Hello's template sets `device.prov.tagSerialNo`), a mismatch with the phone's MAC is recorded on the fetch as `ua_mismatch` and shown, but not denied: User-Agents are trivially forged and some firmwares omit them, so they are evidence, not authentication.
  - The client IP is the TCP peer, or the last `X-Forwarded-For` hop added by a proxy in `HELLO_PROV_TRUSTED_PROXIES` (CIDRs; on kw the pod CIDR `10.42.0.0/16`).
- [S-7] **Vendor file sets (first-class).** Each first-class vendor has a built-in file set: the names its phones request, the format, and a built-in template per file. MAC-bearing names are matched case-insensitively, because vendor guides and integrators disagree on case (Fanvil, Snom). The names, keys and sources are in the vendor reference table below; in short:
  - **Yealink:** an optional boot file (y000000000000.boot or the per-MAC .boot), the model common file y0000000000XX.cfg (XX is the model ID, e.g. 96 for the T54W; a built-in table maps model to ID), then the per-MAC .cfg (lowercase MAC). The per-MAC -local.cfg and -contact.xml requests are answered with an empty 404. Format: a first line "#!version:1.0.0.1", then key = value lines.
  - **Poly (UC Software on VVX; PolyOS on Edge E and CCX):** the per-MAC .cfg (lowercase), falling back to the master 000000000000.cfg. Hello serves a per-MAC master whose `CONFIG_FILES` names one Hello file per phone (the MAC plus "-hello.cfg") and whose `APP_FILE_PATH` names the pinned firmware. Poly phones PUT the MAC plus "-phone.cfg", "-web.cfg", "-app.log", "-boot.log" and "-directory.xml" back; Hello accepts and discards them (S-4). Format: XML, parameters as attributes (`<polycomConfig>` with `reg.1.*`, `device.*`; `device.set="1"` so `device.*` applies).
  - **Grandstream:** cfg plus MAC (legacy binary), the same with .bin, the same with .xml (lowercase), then cfg plus model with .xml, then cfg.xml. Hello serves the MAC .xml name and answers the others with an empty 404. Format: `<gs_provision version="1">` with the phone's `<mac>` (the phone checks it) and P-values.
  - **Snom:** the provisioning URL Hello hands out ends in "{mac}", a placeholder the phone expands to its uppercase MAC, so the phone requests the token path plus its MAC; without a filename the phone requests snom plus model .htm, then snom plus model plus "-" plus MAC .htm, then the firmware .htm files, and Hello answers all of these for the token's phone. Format: XML `<settings><phone-settings>` with `idx`/`perm` attributes.
  - **Fanvil:** the model common file (Fanvil's per-model names such as F0V00X600000.cfg for the X6, from the table in Fanvil's guide) and the per-MAC .cfg. Format: the text form that starts "<<VOIP CONFIG FILE>>Version:2.0002" with sections and ends "<<END OF FILE>>".
  - The User-Agent is recorded on every fetch. Yealink, Grandstream and Fanvil put the MAC in it; Poly does so only when `device.prov.tagSerialNo` is set (off by default), which Hello's Poly template turns on; Snom's format is unconfirmed (S-6 treats a User-Agent as evidence only).
  - Model-ID tables and per-firmware variations live in the built-in file sets (`internal/prov`), and the lab test (S-18) pins each vendor's request sequence.
- [S-8] **Generic per-model templates.** `/api/v1/prov/templates` CRUD. A template (rendered with Go `text/template` in the new `internal/prov` package; versions are audited like `store.Device` changes) has a vendor (or `generic`), a model glob (`T5*`, `GXP21??`, `*`), a list of files, each with a file-name pattern using the variables `{mac}`, `{MAC}` and `{model}` and a body in Go `text/template`, a content type, and a priority.
  - Built-in templates for the five first-class vendors ship in the binary (embedded), are read-only and listed with `builtin: true`. "Copy to edit" creates an editable copy with a higher priority; deleting the copy restores the built-in.
  - Resolution for a request: the phone's explicit override, else the highest-priority template whose vendor and model glob match the phone, ties broken by the more specific glob, then the lower id. A phone with no matching template gets `404` and a `no_template` fetch record.
  - A `generic` template makes any brand work: the administrator writes the file names the phone requests and the body in that phone's format.
  - **Variables** (a fixed, documented struct; nothing else is reachable from a template): `.Phone` (MAC in both cases, model, label, AdminPassword), `.Line` (username, authName, password, displayName, label, domain), `.Server` (host, port, transport, expiry), `.BLF` (list of number, label, uri), `.Prov` (URL, CA URL, resync seconds), `.Firmware` (URL, version, or nil), `.Time` (zone, NTP), plus template functions `xml` (escape), `upper`, `lower` and `default`. No function reads files, the network or the environment.
  - **Validation on save:** the template must parse, every file pattern must be a valid name with only known variables, and a render against a sample phone must succeed within 100 ms and produce at most 256 KiB; failures return `400` with the failing file and line.
  - Every template change is audited and versioned (the previous body is kept), like configuration changes.
- [S-9] **Preview.** `GET /api/v1/phones/{id}/preview?file=<name>` renders exactly what the phone would get for that file, with the SIP secret, the admin password and the token replaced by `********`, so administrators can debug templates without exposing secrets (the only shape that carries a secret stays `deviceWithSecret` in `internal/api/handlers.go`). The preview does not count as a fetch.
- [S-10] **DHCP option 66 and trust on first use.** This replaces the hand-typed setup of `docs/phones.md` for DHCP phones. The Phones settings screen shows, per vendor, the exact value to put in the DHCP server (`http://prov.hello.kw.watteel.lab/p/boot/` on kw; Poly also reads option 160, Yealink also accepts option 43), and the provisioning guide, docs/provisioning.md, gives MikroTik RouterOS and ISC/Kea snippets. Option 66 gives every phone the same URL, so a DHCP phone has no token yet; it gets one by trust on first use:
  - Every new phone starts **armed** for a boot hand-off. The boot path serves each vendor's common file with no secrets: the CA install, the re-check settings and the provisioning URL of the boot path itself.
  - The first per-MAC boot request of an armed, allowlisted phone gets a bootstrap file carrying only the CA and the phone's per-device HTTPS URL (token included), with no SIP secret and no admin password. The phone is then **disarmed** in the same transaction, the fetch is recorded as `boot_handoff`, and from then on the phone fetches over HTTPS with its token.
  - A later boot request for a disarmed MAC gets an empty `404`, is recorded as `boot_reclaim` and flags the phone `boot reclaimed` in the UI, because either the phone was reset or someone else is claiming its MAC.
  - **Re-arm:** `POST /api/v1/phones/{id}/rearm` (audited) rotates the token at once (`immediate`, since the old one is either lost with a reset phone or claimed by someone else) and arms the phone for one more hand-off.
  - Optional `HELLO_PROV_BOOT_CIDRS` restricts hand-offs to the phone networks; a request from elsewhere is recorded as `boot_denied` and does not disarm.
  - The token crosses plain HTTP once in the hand-off. This is the accepted cost of trust on first use and does not set `token exposed`; the guide says so.
  - Phones provisioned by redirect or a typed URL already have their token; their first HTTPS fetch disarms them, so the boot path never hands out their token.
- [S-11] **Vendor redirect services (pluggable).** Documented in the provisioning guide next to `docs/phones.md`. One client per vendor behind one Go interface (`Check()`, `Register(mac, serial, url)`, `Unregister(mac)`), selected by vendor. The research (vendor reference table) found very different realities, so each client states what it can do (`Capabilities`: registers a URL, needs the serial number, supported at all):
  - **Snom SRAPS:** supported. The REST API (Hawk HMAC-SHA256 with an access key ID and secret) sets the endpoint's `setting_server` to the phone's URL; the older XML-RPC `redirect.registerPhone(mac, url)` is the fallback.
  - **Yealink RPS:** supported. The RPS JSON API (signed with an access key and secret) registers MACs with a per-device `uniqueServerUrl` against a server entry Hello creates once. Yealink's newer YMCS API needs the serial number as well, or MAC-only registration enabled on the account by Yealink; the client uses YMCS only when its settings say so.
  - **Grandstream GDMS:** supported, with a limit. The API adds a device but requires its serial number, and no documented call binds a MAC to a URL; the client adds the device to the configured GDMS site, and the administrator sets the site's provisioning server once in GDMS. That site URL is the boot path, so a GDMS phone gets its token through the S-10 hand-off. The UI says so.
  - **Poly:** manual. PDMS-SP was shut down on 30 May 2025 in favour of Poly ZT, whose API is not public; the older ZTP XML API needs a separately requested account and cannot create the profile. The client returns `ErrUnsupported` and the UI shows the manual step (paste the URL into the Poly portal).
  - **Fanvil FDPS:** manual. FDPS has no public API documentation (only an undocumented XML-RPC endpoint used by third parties); the client returns `ErrUnsupported` and the UI shows the manual step.
  - Phones gain an optional serial-number field for the vendors that need it.
  - Credentials per vendor are entered in the UI (`/api/v1/prov/redirect/{vendor}`), sealed under `HELLO_SECRET_KEY` with `internal/secret` (AAD `redirect:<vendor>`), write-only like trunk passwords (`hasCredentials`), and tested with `Check()` on save.
  - With credentials, creating, rotating or deleting a phone of a supported vendor registers, re-registers or unregisters its MAC with the phone's per-device URL (token included), asynchronously with retry (exponential back-off to one hour, giving up after 24 hours). The phone's redirect status (`not_configured`, `manual`, `pending`, `registered`, `failed: <reason>`) is shown in the inventory.
  - Without credentials nothing is called and the status is `not_configured`; DHCP and manual entry work the same either way.
  - **Credentials from the deployment:** on kw the credentials come from the sops-encrypted Secret `hello-prov-redirect` (file `secret-hello-prov-redirect.sops.yaml` beside the other kw secrets), mounted as env on hello-control. Credentials present in env take precedence over the UI and show there as "set by the deployment" (read-only). Keys and env names:
    - Snom SRAPS: `snomSrapsAccessKeyId`, `snomSrapsAccessKeySecret` → `HELLO_PROV_SNOM_KEY_ID`, `HELLO_PROV_SNOM_KEY_SECRET`
    - Yealink RPS: `yealinkRpsAccessKey`, `yealinkRpsAccessSecret` → `HELLO_PROV_YEALINK_KEY`, `HELLO_PROV_YEALINK_SECRET`; Yealink YMCS (used when set): `yealinkYmcsClientId`, `yealinkYmcsClientSecret`, `yealinkYmcsRegion` → `HELLO_PROV_YMCS_CLIENT_ID`, `HELLO_PROV_YMCS_CLIENT_SECRET`, `HELLO_PROV_YMCS_REGION`
    - Grandstream GDMS: `gdmsClientId`, `gdmsClientSecret`, `gdmsUsername`, `gdmsPassword`, `gdmsRegion`, `gdmsSiteId` → `HELLO_PROV_GDMS_CLIENT_ID`, `HELLO_PROV_GDMS_CLIENT_SECRET`, `HELLO_PROV_GDMS_USERNAME`, `HELLO_PROV_GDMS_PASSWORD`, `HELLO_PROV_GDMS_REGION`, `HELLO_PROV_GDMS_SITE_ID`
    - live-test devices (one real phone per vendor that the user owns, since the vendor services reject unknown MACs): `liveTestSnomMac`, `liveTestYealinkMac`, `liveTestYealinkSerial`, `liveTestGdmsMac`, `liveTestGdmsSerial`
  - **Live tests are gated on those secrets.** `TestRedirectLive` runs against the real vendor services only when `HELLO_PROV_LIVE_REDIRECT=1` and the vendor's credential and live-test keys are all present; otherwise it skips that vendor and says which key is missing. A skipped vendor is reported as not verified, never as passed.
- [S-12] **TLS and exposure on kw.** Provisioning is published on its own host, `prov.hello.kw.watteel.lab` (the lab's wildcard DNS already resolves `*.kw.watteel.lab` to the ingress, 192.168.10.120), through its own Ingress on the existing ingress-nginx:
  - HTTPS with a cert-manager `Certificate` from the cluster's `cluster-ca` ClusterIssuer (the pattern kuvryn-ai uses on kw), and plain HTTP left open (`ssl-redirect: "false"`) only because the DHCP bootstrap and the CA download need it; per-device paths refuse plain HTTP (S-6).
  - Access logging off on this Ingress (`enable-access-log: "false"`), because the token is in the path; Hello's own fetch audit (S-14) records the path with the token redacted.
  - No phone's built-in trust store contains `cluster-ca`, and the research shows the defaults refuse it: Yealink accepts only trusted certificates by default, Poly checks certificates and names by default, and Snom fails on an unknown CA. A phone sent straight to an HTTPS URL (redirect or manual entry) therefore fails its first fetch until Hello's CA is installed. Each built-in template installs the CA from the plain-HTTP CA URL where the vendor has a key for it (Yealink `static.trusted_certificates.url`, Poly `device.sec.TLS.customCaCert1`, Grandstream's CA slots P8433–P8438; Snom's and Fanvil's keys are unconfirmed), and the DHCP boot path (S-10) delivers that first. Manual entry documents the one-time CA upload in each phone's web UI. A publicly trusted certificate would remove this step but was not chosen (decided 2026-10-06); the boot path of S-10 is how a DHCP phone gets the CA before its first HTTPS fetch.
- [S-13] **Firmware hosting.** `/api/v1/prov/firmware` uploads a firmware file (multipart, up to 512 MiB) with vendor, model glob and version; Hello stores it in MinIO (bucket `hello-firmware`, created on first use, same `MINIO_*` settings as Phase 4) with its size and SHA-256, and streams it to phones at `/p/<token>/fw/<file>` with `Range` support. A model can pin one firmware version; a pinned version adds the firmware URL to the rendered config and the phone upgrades at its next check. Unpinned models get no firmware URL. Firmware is served only under a valid token, never on `/p/boot/`.
- [S-14] **Fetch audit.** Every request to the provisioning listener, served or denied, writes one `prov_fetches` row: time, phone (when the token or MAC resolved one), MAC claimed by the file name, source IP, User-Agent (truncated to 256 bytes), the path with the token redacted (`/p/****/…`), the file kind, the result (`served`, `not_modified`, `unknown_token`, `mac_mismatch`, `not_allowlisted`, `plain_http`, `rate_limited`, `no_template`, `render_error`, `boot_served`, `boot_handoff`, `boot_reclaim`, `boot_denied`, `upload_discarded`), the status code and the bytes sent. Rows older than `HELLO_PROV_AUDIT_RETENTION` (default 90 days) are pruned daily. Writes are buffered and batched off the request path; a database outage drops audit rows with a counter, never the response.
- [S-15] **Rate limiting.** Cluster-wide in Valkey (hello-control runs two replicas on kw), per source IP: at most 60 requests per minute, and at most 10 denied requests per 10 minutes, after which that IP gets `429` for 10 minutes for every path. Per phone: at most 30 served config files per hour. Limits are `HELLO_PROV_RATE_*` settings. When Valkey is unreachable, each replica enforces the same limits in memory (never fails open). Rate-limited requests are audited (`rate_limited`) without rendering.
- [S-16] **Console screens.** Credentials and secrets follow the write-only pattern of `web/src/pages/Trunks.tsx` and the show-once dialog of `web/src/pages/Devices.tsx`; the new pages are linked from `web/src/nav.ts` and consume only the API that `internal/api/handlers.go` serves.
  - **Phones** (`/phones`, in the Directory group): the inventory table (MAC, vendor and model, extension and device, label, last fetch time and IP, firmware from the User-Agent, redirect status, flags such as `token exposed`, `ua_mismatch`, `boot reclaimed`, and whether the phone is armed for a boot hand-off), a re-arm action, reveal and rotate of the admin password (S-20), filters, create and edit with a device picker that states the secret-rotation consequence, BLF key editor, rotate-token (shows the new URL once with a copy button), delete, and a fetch-log tab per phone.
  - **CSV import** on the Phones page: columns `mac,vendor,model,extension[,label][,blf]`; a dry run lists per-row errors (bad MAC, unknown extension, duplicate MAC, unknown vendor), then an apply commits all rows in one transaction or none.
  - **Templates** (`/phones/templates`): built-ins and copies, a code editor with the variable reference beside it, server-side validation errors shown at the line, and a preview against a chosen phone (secrets masked, S-9).
  - **Firmware** (`/phones/firmware`): upload with progress, list with size and SHA-256, pin per model.
  - **Provisioning settings** (`/phones/settings`): the computed DHCP option values per vendor, the CA certificate download, and one card per redirect vendor with write-only credentials, a Test button and its status.
- [S-17] **Metrics.**
  - `hello_prov_requests_total{vendor,kind,result}` (kind: `common`, `device`, `firmware`, `ca`, `boot`, `upload`, `other`)
  - `hello_prov_render_seconds` (histogram)
  - `hello_prov_phones{state}` (`never_fetched`, `fetched`, `stale` when the last fetch is older than twice the re-check interval)
  - `hello_prov_redirect_ops_total{vendor,op,result}`
  - `hello_prov_firmware_bytes_total{vendor}`
  - `hello_prov_audit_dropped_total`
- [S-18] **Lab and vendor emulation.** `test/provclient` is a Go package that requests files exactly as each first-class vendor does: the same path sequence, MAC case, User-Agent and fallbacks, for one representative model each (Yealink T54W, Poly VVX 450, Grandstream GRP2614, Snom D785, Fanvil X5U), over HTTPS with the lab CA. It parses the vendor format (key/value, Poly XML, Grandstream P-values, Snom XML, Fanvil sections) back into a neutral `{server, port, user, authUser, password, displayName, blf[], provURL, firmwareURL}`. The lab test uses it to fetch every vendor's files from hello-control, then registers a `test/sipua` phone with the extracted credentials through Kamailio and expects `200 OK`.
- [S-19] **Documentation.** the new provisioning guide, docs/provisioning.md,: adding phones and the CSV format; DHCP option 66/160/43 values per vendor with RouterOS and ISC/Kea examples; manual URL entry per vendor (where in each phone's web UI); the CA trust step; redirect services; writing a generic template; token rotation and the `token exposed` flag; the security model and its limits. `docs/phones.md` links to it as the preferred path.
- [S-20] **Phone admin password.** Every phone gets a random admin (web UI) password of 20 characters on create, sealed with `secret.Box` (AAD `phone-admin:<id>`) in a new column of `phones`. The built-in templates set it with each vendor's admin-password key, and generic templates see it as `.Phone.AdminPassword`. It is served only over HTTPS with the token, never on the boot path, and masked in previews. `POST /api/v1/phones/{id}/admin-password/reveal` returns it to an administrator and writes an audit row; `POST /api/v1/phones/{id}/admin-password/rotate` sets a new one, which the phone picks up at its next fetch.

## Out of scope

- TFTP and FTP provisioning: secrets never travel over them, and Hello does not run a TFTP server.
- Pushing a re-sync to a phone (SIP `NOTIFY Event: check-sync`). Phones re-check on their interval or on reboot; a "re-sync now" button is a later addition.
- Vendor factory-certificate (mutual TLS) authentication of phones. Tokens are the authentication; client certificates can be added later where ingress and vendors support them.
- Storing anything a phone uploads (logs, Poly override files, call lists, contact directories).
- Phone-book / contact-directory provisioning, wallpapers, ringtones, expansion-module layouts beyond BLF keys, and multi-line (more than one account per phone) setups.
- DECT base stations and multi-handset systems (one account per handset is a different inventory model).
- Running the DHCP server, or configuring the customer's DHCP server automatically.
- SIP over TCP/TLS and SRTP in the rendered configs (Hello is UDP-only).

## Constraints

- No PostgreSQL call on the SIP path; provisioning lives entirely in hello-control. hello-sip is unchanged apart from nothing: credentials it verifies are still the HA1 values (S-2 keeps them in step).
- **Secrets:** a SIP secret, a phone admin password, a provisioning token or a redirect credential never appears in logs, API responses (beyond the show-once create/rotate responses and the audited admin-password reveal), metrics, the fetch audit, previews or traces. The fetch audit and every log line redact `/p/<token>/` to `/p/****/`. The kw provisioning Ingress has access logging off.
- **Template safety:** admin templates are Go `text/template` over a fixed data struct with no methods that reach outside it; each render has a 100 ms deadline and a 256 KiB output cap. Templates are administrator-only (the same role that manages devices).
- **Performance:** a cached-ETag re-check answers in under 5 ms p99 at hello-control, and a full render under 20 ms p99 (benchmark in `internal/prov`). Rendering never blocks on Valkey for longer than the rate-limit call's 50 ms timeout.
- **Determinism:** the same phone and configuration render byte-identical bodies (stable ETag), so phones do not re-apply unchanged configs.
- **HA:** both hello-control replicas serve provisioning; nothing is replica-local except the in-memory rate-limit fallback.
- **Deployment:** kw via Kuvryn Sync (`deploy/kuvryn-sync/kw/resources.yaml`); no workloads on the user's Mac; CI on the Arc runners.
- **New dependencies:** none planned (stdlib `text/template`, `encoding/xml`, `crypto/*`; MinIO, Valkey and Postgres clients already present).
- Gate per task: gofmt, `go vet`, golangci-lint (0), `go test -race ./...` green, `procoder check` 0 blocking, mutation checks; REVIEW.md applies.

## Edge cases

- The same MAC is entered twice (in two rows of a CSV or on two phones): rejected with the conflicting row or phone named.
- Two boot requests for the same armed MAC arrive together (a spoofer racing the real phone): the disarm is a conditional update, so exactly one gets the token; the other gets `boot_reclaim`. If the spoofer won, the real phone's next boot request flags `boot reclaimed`, and the administrator re-arms, which revokes the spoofer's token.
- A factory-reset phone boots through DHCP again: it is disarmed, so it gets `404` and the `boot reclaimed` flag until an administrator re-arms it.
- A phone is moved to another extension: its device binding changes, the new device's secret is rotated and sealed, the old device keeps its HA1 values, and the phone gets the new account at its next fetch.
- A phone requests a file that embeds a different MAC with its own valid token (a cloned config or a mistyped URL): `mac_mismatch`, `404`, audited.
- A previous-grace token and a current token are both used (two phones sharing a token after a clone): both are served until the grace ends, the fetch log shows two IPs and User-Agents for one phone and the UI flags `ua_mismatch`; the administrator rotates with `immediate=true`.
- A model has no built-in and no matching generic template: the phone is created with a warning ("no template matches this model"); its fetches record `no_template`.
- A template renders differently for one phone because of its data (e.g. an empty BLF list): the validation sample covers empty and full BLF lists, and `default` is available for optional values.
- A firmware pin points at a file whose upload was deleted: the pin is refused while referenced (`409`), so a rendered URL never points at a missing object.
- Poly's master file is requested as `<mac>.cfg` and then `000000000000.cfg`: Hello serves the per-MAC master, so the fallback is never needed for a known phone.
- A Yealink model whose hardware ID is not in the built-in table: its common file is not recognised, only `<mac>.cfg` is served, and the UI shows "unknown model ID"; the administrator can still use a generic template.
- Clock skew between the two hello-control replicas: rate-limit windows live in Valkey with server time, so they agree.
- A redirect API call succeeds but the vendor portal later shows a different URL (changed by hand): `Check()` and a daily reconcile report the drift as `failed: drift`.

## Failure modes

- **Valkey unavailable:** rate limiting falls back to per-replica memory limits; provisioning keeps serving.
- **PostgreSQL unavailable:** provisioning answers `503` with `Retry-After: 300` (phones retry); the management API is unavailable as in Phase 1. No cached secret-bearing configs are kept in memory beyond a request.
- **MinIO unavailable:** firmware requests answer `503`; config files still render (a pinned firmware URL is still written, the phone retries the download).
- **`HELLO_SECRET_KEY` cannot open a sealed secret or token:** that phone's config fetch answers `404` with `render_error`, a loud log line (without the value) and a UI flag; no partial config is served.
- **A vendor redirect API is down or rejects credentials:** the phone's redirect status shows `failed` with the vendor's error; retries back off; DHCP and manual entry are unaffected.
- **A phone cannot verify the HTTPS certificate:** it never reaches Hello's per-device path; the fetch log shows only its `/p/ca.crt` or `/p/boot/` requests (or nothing), and the UI's "never fetched" filter plus the new provisioning guide, docs/provisioning.md,'s CA section is the diagnosis path.
- **The rate limit trips during a mass reboot** (a site power cut brings 200 phones up at once): limits are per IP and per phone, not global, so phones behind distinct IPs are unaffected; a site behind one NAT IP is the documented case for raising `HELLO_PROV_RATE_IP_PER_MIN`.
